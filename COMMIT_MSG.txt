unarchive: batch L1, Linux hosts - name rules follow the detected OS

New requirement: extraction fully compatible with Linux, keeping all the
Windows behaviour. The server's OS is detected (os.name): Windows keeps
every rule built so far, unchanged; Linux lifts the Windows-only refusals
so archives extract as GNU tar and unzip extract them there; any other OS
is refused. Each run logs the rules it applied and publishes
${hostRules}.

On Linux: drive letters, ':', Windows-forbidden characters, reserved
names, trailing dot/space and case-only differences are kept as names;
'\' is a character in tars and a separator only in zips made on MS-DOS
(what unzip does, measured); names are limited to 255 UTF-8 bytes;
maxPathLength defaults to auto (259 characters on Windows, 4096 bytes on
Linux). Leading '/', 'a/./b', 'a//b', duplicates and '..' stay refused.

runUnarchive accepts maxPathLength=auto and publishes hostRules; the
designer seeds auto and says the rules follow the server; USAGE.md gains
"Windows and Linux servers".

Measured on Linux: GNU tar extracts every Windows-illegal name as is;
unzip converts backslashes only for made-by host 0; Debian's unzip
mangles UTF-8 names of jar zips, where the step follows the zip's flag.

Verified: Windows suites unchanged (232 + 194); Linux suite 140 with GNU
tar / unzip parity; wiring 90; panel 114; guide 43; designer XML through
the real parser to runUnarchive; 24 mutations, all caught.

Not verified: mvn clean package, a run in the container, a real Linux
server deployment.
