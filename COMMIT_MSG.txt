json2csv batch 0 revised: Gate 0 answered, and it removed parameters

Specification updated at .claude/JSON_TO_CSV_EXECUTOR.md. Still no code.

WHAT THE ANSWERS DID

Six questions answered, four of them deleting a parameter each: documentsPath,
onSiblingArrays, onEmptyArray, checkNullable with onNullViolation and the
${nullViolations} counter, COLUMN_EXTENSION, and epoch milliseconds from the
date defaults. A parameter specified for a case that does not exist is a thing
to misconfigure, so they are gone rather than left switched off.

ONE FILE, ONE ROW

Each JSON is a serialised database row. One file is one document is one CSV
row, and multi-row flattening - one row per array element with outer values
repeated - is deferred. ${filesRead} must equal ${rowsWritten}, and the step
log says so rather than leaving it to be worked out: it is the cheapest
possible assertion that the executor did what it claims, and the one number a
gate can branch on.

The deferred design stays on the page, marked DEFERRED, not deleted. The
refusal below is only defensible if what is being refused is written down, and
the chain rule is the design for the day it returns.

[] IS REFUSED, NOT GUESSED AT

An unbounded [] fails static validation, before a file is opened. It is never
read as [0] and never ignored. Reading it as [0] would deliver a feed short by
every element after the first, with nothing in the output saying so; ignoring
the column would deliver it empty. Both are discovered in ELAR months later.
This is discovered when the step is saved.

The path catalogue still SHOWS array paths, marked unavailable with that
reason. Hiding them would leave an operator hunting for an attribute that is
plainly in the sample.

conti[0], an explicit index, is added, and it is the one place this design
goes past Gate 0: a file may carry arrays while only one row comes out, and an
explicit index reaches into one without asking for the deferred half. It is
flagged in the spec as veto-able at this gate.

DATES

Three masks tried in order - YYYY/MM/DD, YYYYMMDD, YYYY-MM-DD - and the spec
says why order is safe here rather than assuming it. The three are disjoint by
shape: eight digits, or ten with slashes, or ten with dashes, so no value
parses as two of them. A format list tried in order is a dangerous idea in
general - DD/MM/YYYY then MM/DD/YYYY reads 03/04 as two different days and
never says so - and is safe only when the shapes are disjoint. A fourth mask
added later is not automatically safe and must be checked against the other
three.

Parsing is STRICT, on the uuuu that fmtToJavaPattern already produces:
20260230 is refused rather than quietly resolved to the 28th. A Date column
exists to validate as much as to reformat, and a resolver that repairs
impossible dates gives the validation away. A JSON number needs no special
case: 20260824 is written plain and parses under YYYYMMDD.

SMALLER GUARDS, CLOSER TO REALITY

maxFileMB drops from 64 to 16. A guard set far above anything real cannot
catch a whole export dropped into the input directory by mistake, which is
most of what it is for.

renameProcessed can only ever fire at the end here, unlike elarxml where it is
per file as soon as that file's batches have reached their final names: every
input feeds one output, so nothing is processed until the step is. Renaming
earlier would be the elarxml .done defect reintroduced from the other side.
