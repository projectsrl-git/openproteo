objpack: withdraw the claim that the spec contradicts itself on the name

A correction, not a feature. No behaviour changes and no test changes.

WHAT WAS WRONG. Batch 5 recorded, in six places, that the specification
contradicted itself about the name of a compressed archive and that the
code therefore had to choose one. That was overstated. Section 3.5 names
the resulting files itself - "resulting in a .tar.gz file", and .tar.bz2
and .tar.xz for the other two - and section 2's pattern ends in .*, a
wildcard, so those names satisfy the naming convention without strain. The
.tar examples elsewhere are the uncompressed case, not a rule against the
rest. There was no conflict to resolve, only one I had read into it.

Corrected in SubmissionName.archive's javadoc, USAGE.md, CLAUDE.md, the
executor spec, the batch-5 note and item 4 of the transcription's
contradiction list. Item 4 now says what is genuinely unstated - whether
compression is expected or merely tolerated - instead of claiming a
contradiction that is not there.

WHY THE ARCHIVE IS STILL NOT JUST NAMED .tar. Raised as a way to satisfy
both readings, and rejected on measured evidence rather than taste. A gzip
stream renamed .tar: GNU tar -tf and -xf unpack it, python tarfile in its
default mode unpacks it, python in forced-uncompressed mode fails with
"truncated header", and a parser reading ustar headers directly finds no
magic at offset 257 at all - the category that includes commons-compress,
strict system tars and UstarReader here. Which one Transarch uses is
undocumented.

The failure modes are asymmetric, and that is the deciding argument. A
wrong extension is rejected at the naming validation: early, loud, with the
source data still in place. A compressed file wearing a .tar name passes
both the size check and the checksum check and breaks later, at extraction,
possibly after the source has been decommissioned. In a legal archive the
second is the one you cannot afford.

THE DEFAULT, NOW STATED RATHER THAN INFERRED. compression defaults to none
and delivers an uncompressed <base>.tar, byte for byte what the PowerShell
script produced. A feed that never sets the parameter is unaffected by
anything in the compression work. USAGE.md now opens that section by
saying so, instead of leaving it to be worked out from a parameter table.

VERIFIED: javac --release 8 on the package after the javadoc edit; 103
suite assertions and 26 mutations re-run, all green; a default run still
produces a file that `file` reports as "POSIX tar archive"; 33 of 33
parameters still documented; code fences balanced; no stale claim of a
contradiction left anywhere except the transcription's own preamble, which
is about the four contradictions that are real.

NOT VERIFIED: still nobody has confirmed the archive accepts .tar.gz. That
is the one answer that would settle this, and until it arrives the default
is the conservative one.
