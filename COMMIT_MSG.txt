Spec: audit-proof SQL report executor, workflow versioning on structural edits, missing steps in Variables

Design and handoff spec for the three requested changes, committed before any implementation so the
decisions are made explicitly and each batch can be reviewed on its own.

The sqlreport executor runs a list of read-only queries and produces a Markdown document rather than a
CSV: each query with its own execution timestamp and duration, the text as executed after variable
substitution, the datasource host, user and database, the run id, the row count and the result table. It
is a new executor rather than a mode of sql, because sql exists to move data while this one exists to
prove something, and the deliverable is the document itself. Read-only is enforced in two layers, a
statement check and a read-only connection, and the spec states plainly that the real guarantee is the
database account's own rights. Variable collection is specified with a decision left open: aligned
semicolon-separated lists, which reuse the existing list indexing and OUTPUT DATA rendering, or a new
keyed resolver syntax that is more expressive but touches VarResolver.

Workflow versioning proposes a copy with the id suffixed .v1 when steps are added or removed on a feed
that already has runs, with the open questions spelled out: whether the original keeps the schedule, and
whether a dotted suffix is acceptable in a feed id given those ids appear in paths and in the Legal
Archive naming.

The Variables page change lists steps present in only some of the selected feeds as greyed-out disabled
rows with a badge, and an action to add them to all selected feeds; the spec flags that the insertion
position must be explicit, and asks what to do when the same step id carries a different executor.

No code changes.
