objunpack: read metadata row by row; fail properly when out of memory

On AIX a real package of 100 000 objects (metadata 52 MB) was read in
57 s, then the step stayed at "reading ...metadata.csv" for hours.

Reproduced on Java 8 with a package of the same shape: with a 512 MB
heap the step ran out of memory at exactly that line - it held the
metadata as one string plus every cell, about ten times its size. And
an OutOfMemoryError is caught by nothing on the step's path: the run
pool logs it and the step stays RUNNING.

- PsCsvReader: one parser over a Reader, with a record-by-record
  entry point; the string entry point runs through it. filerename is
  called as before.
- ObjectUnpack reads the metadata record by record and keeps per
  object its name, mime type and row number only. Heartbeat and Stop
  while reading it and while matching. More rows than maxObjects are
  refused. The 512 MB cap on the file is gone.
- runObjUnpack ends the step with exit 1 and a message naming the heap
  when the JVM runs out of memory.

Same package after the change: completes with a 256 MB heap in 13 s.
Not solved here: objpack, next in the chain, ran out of memory with
512 MB on the same rows and needs 1 GB. Proposed, not done: catching
Throwable in InternalSteps.run for every executor.

No parameter added or removed. USAGE.md, the objunpack and filerename
specs updated. README.md and CLAUDE.md not touched.

Verified on Linux (sandbox; Temurin 1.8.0_432 and JDK 21.0.12 both
run; root and uid 65534; LANG=C.UTF-8): old parser against new on
300 000 fuzzed inputs and a 70 MB file, identical; old ObjectUnpack
against new on 31 packages from the real producers under 7
configurations, 217 outcomes identical; 47 assertions on the new
behaviour; 27 mutations, all caught; the lifted runObjUnpack under a
100 MB heap; differential compile identical; git apply --check on a
second clean clone.
Verified on Windows: nothing.
Verified on AIX: nothing. The author's run there found the defect.
Not verified on any: IBM's JVM; the suites of the earlier batches,
lost with the sandbox - their code is not touched here; mvn clean
package.
