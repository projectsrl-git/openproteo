objpack: Transarch object-feed spec transcription and Gate 0

Batch 0 of the object-submission packager. No code: two documents in
.claude/, per the spec-first rule.

TRANSARCH_OBJECT_SUBMISSION_SPEC.md transcribes the UBS Confluence page
"Object (e.g. pdf, jpeg, xml, json)" (pageId=1221950108) from screenshots,
because the page is unreachable from where the executor is developed. It
covers the naming convention, the audit JSON, the metadata CSV and its
mandatory fields, object-file naming and OID padding, the control file,
the TAR package and the MD5 checksum, and the validation rules. Section 6
records five contradictions that are IN THE SOURCE and are not resolved
here: version padding V001 vs V1, OID padding by count vs the examples,
mime type as dotted extension vs media type, whether compression is
permitted for a .tar-named submission, and the type of object_id.

OBJECT_PACKAGE_EXECUTOR.md is the design. Three points answer questions
asked directly, and two of them are measured rather than argued:

- samples/dataschema.json and the Transarch metadata schema have the SAME
  shape, [{"name","nullable","type"}]. The feed's existing dataschema is
  therefore usable as-is for pre-flight validation of column order and
  nullability. It is NOT a package member: it appears nowhere in the tar
  listing, and shipping it would add an unexpected member.
- tar -cf t.tar -C stg -- f1 f2 stores BARE member names, magic "ustar ",
  no "./" prefix. The PS1 script's ^[.][/\] normalisation defends against
  a tar that prefixes them; it does not describe the expected output.
- The tar writer will be hand-written ustar in pure JDK. Java 8 has no tar
  anywhere, and commons-compress cannot be confirmed on the internal Nexus
  from this sandbox, so a dependency-based design might have to be redone
  after the fact. ustar is small enough to prove against the real GNU tar
  present in the sandbox.

Field mapping is declared on the step as <column role= source=/> children,
with the four mandatory roles falling back to the Transarch names when
unmapped, so a CSV that already uses them needs no mapping at all.
Recursive object lookup is configurable and defaults to no; the object
path may come from a CSV column, resolved against objectsDir and refused
if it escapes it.

The script stages every object into %TEMP% before invoking tar.exe. At the
documented 20 GB ceiling that is 20 GB written and read for nothing; the
Java writer streams from the landing zone.

VERIFIED: the dataschema shapes, by reading both files; the tar member
naming and magic, by running GNU tar and parsing the headers.
NOT VERIFIED: nothing is compiled or run, because nothing was written.

Nine Gate 0 questions in section 9 are open and block batch 1. Five come
from the contradictions above and need Soffici or the onboarding team;
the Accepted Delimiters List page was not captured and is needed before
outDelimiter can be validated rather than merely accepted.
