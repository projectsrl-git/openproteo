tiffcompress, batch 0: specification, and the sample decides the shape

Specification only. No code, no dependency, no registration.

A new internal executor tiffcompress, LOCAL directories only, with mode=SCAN
by default and mode=COMPRESS later. SCAN reads the TIFF header and the IFD
chain - never pixel data - and reports the distribution of compression tag 259
by count AND by bytes, plus how much of the corpus is G4-eligible.

Two packages, one executor. orchestrator.tiff holds the scanner with no write
API, kept read-only by construction and proved by a scan the way elarcheck is
(ELAR_CHECK_EXECUTOR.md section 307). orchestrator.tiffpack will hold
everything that creates, replaces or deletes a file. A writer in the scanner's
package would end that guarantee permanently, and it is what makes a scan safe
to aim at a live directory.

Sampling is the design problem, not the parsing. Three million files means
File.list materialises three million strings before the first file is opened,
so enumeration is lazy; and the sample is not a preview but the proportion
that decides whether batch 2 exists at all. scanOrder=DIRECTORY takes the
first N, which is fast and biased in exactly the wrong way - directory order
tracks creation order, so the first N are one feed from one source system
scanned by one generation of hardware, the variables that determine
compression. Default is RESERVOIR: one lazy pass, unbiased, bounded memory,
opening no more files. The report states the order, the seed, entries
enumerated and files opened, so a number cannot be quoted without its sampling
method.

Batch 2 is named but not designed, because batch 1's numbers decide what it
is: bilevel uncompressed or LZW means G4 and a Nexus dependency; greyscale or
colour uncompressed means G4 does not apply and Deflate from java.util.zip
does, with no dependency; mostly-already-G4 means there is no batch 2. G4 will
not be hand-rolled - a bug in MMR coding yields an image that decodes
correctly in some viewers and wrongly in others.

Three open questions are recorded as the user's, in section 9: whether
TwelveMonkeys imageio-tiff is on the internal Nexus, whether an archived
document may be bytes the source system does not hold given that the INDX
carries the SHA-256 of what is embedded, and how deep the losslessness check
in batch 2 must go.

NOT VERIFIED
- That Java 8's javax.imageio has no TIFF plugin. This is true of Java 8 and
  the reason the dependency question exists, but the sandbox runs a later JDK
  whose ImageIO does ship TIFF, so it cannot be demonstrated here.

  is still unmeasured, and no claim about the distribution is made anywhere in
  it.
