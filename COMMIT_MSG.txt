ftpsend: a target that may store but not stat, and two facts from the field

Reported from the first real run: the transfer succeeds and the step fails.
The log reads 150, 50176 bytes written, 226 Transfer complete - and then SIZE
comes back 550 Operation not permitted, so the verification rule fails the
step and nothing after the first file is attempted.

The rule is right and the situation is one the specification named as open. An
account may be allowed to store and not to stat, and a drop box that collects
the file the moment it lands answers 550 for a different reason that looks
identical from here. Neither is a failed transfer.

The target gains Verify uploads: SIZE, the default and unchanged, or NONE,
which takes the server's 226 as the confirmation. 226 is worth more than it
looks and less than SIZE - it is the server saying it received the stream and
closed the file, which is more than "the file exists", and that distinction is
the whole reason SIZE was there, because a server creates the destination the
moment it accepts STOR. What 226 does not catch is a file truncated without
complaint. So NONE is a real weakening: it warns once in the step log before
anything is sent, and marks each file remoteBytes=unverified rather than
printing a number nobody checked. The SIZE failure message now names the
setting that changes it.

Nothing else is weakened. A refused STOR, a data channel that never opens, a
transfer rejected at the end: all still fail, and all still stop everything
after them.

Two facts from the same log, worth recording because both were open questions.

The data channel works. 227 advertised 10.117.145.81, the client substituted
the control host, the connection opened and 50176 bytes crossed. The wall this
feature was designed around is not there from that machine.

The JVM is not Java 8. The reflection that installs the control session is
refused with "module java.base does not opens sun.security.ssl", so it is 9 or
later, and the transfer completed anyway over a fresh TLS 1.3 session. That
server does not require session reuse - which was the risk that shaped the
whole transport - and the degradation path built for exactly this case behaved
as designed. On that JVM the reuse option is inert unless Tomcat is started
with --add-opens java.base/sun.security.ssl=ALL-UNNAMED, and on this evidence
it does not need to be.
