elarxml batch 1: flat CSV reader, config resolver, blocking pre-scan

First code of the executor. New package com.legalarchive.orchestrator.elar,
deliberately free of Spring and of the orchestrator's own types so that it
compiles and runs on its own - which is why this batch comes first and why it
could be verified here rather than only on deploy. No executor, no
registration, no XML yet.

ElarConfig loads the properties and resolves every key through one path that
prepends the family prefix. A familyType matching nothing is caught at load
and answered with the families the file does contain, replacing the production
NPE that came from copying a .bat between feeds and leaving one argument
unchanged - the old failure said nothing about which key or which file. A
missing required key, and a value that should be a number and is not, name the
key, the file and the value. The three keys the legacy tool read without a
prefix still work bare, with a prefixed form taking precedence.

docIdTag performs the translation the legacy Validator never did.
doc_id_reference holds a CSV column name while the duplicate checks are keyed
by ELAR tag name, so the reference lookup returned null for every document and
the check threw on the first row of any file - it could never have passed. The
asymmetry is real in the properties file, since not_duplicated_tags_list is
already expressed in tag names, so it is handled explicitly rather than
normalised away, and a doc-id column with no mapping is refused naming the key
that is missing. contentTag and dsakTag are configurable per family, because
every family has its own template with its own tags, and default to this
family's names so an existing properties file needs no edit.

FlatCsvReader reads with one explicit charset and REPORT by default, against
the legacy pipeline which read the same data through three different decoders
- hardcoded UTF-8 in one half, platform default in the other two. It splits
with a limit of -1 so trailing empty fields survive, where the legacy split
dropped them and a row ending in empty columns then looked like a field-count
mismatch. Quoting is optional and disabled by default, keeping the parse
identical to legacy. A BOM is stripped from the header rather than becoming
part of the first column name. A decoder failure is rewritten to name the
file, the line, the approximate byte offset and both ways out; the offset is
stated as approximate because the reader buffers ahead, which is better than
printing a precise-looking number that can be wrong by up to 64 KB.

ElarPreScan is the blocking scan: every input file checked before a single
byte of output exists, for field-count mismatches and for referenced content
files that do not exist. It reports every offending line across every file in
one message, capped at fifty listed per category with the full count kept, and
it never prints a row's content - only file names, line numbers and the
missing document's name, which is a document identifier rather than a customer
one and without which the operator cannot act. A malformed row is not then
also counted as a missing file, because its content path cannot be trusted
either. It reuses FlatCsvReader rather than reimplementing the parse, which is
what makes "a file that passes the scan cannot fail the read" true by
construction instead of by intention. resolveContentFile re-roots on the file
name only, as the legacy updateFilePath did, which also means a value carrying
a directory traversal cannot escape documentPath.

Verified with 62 assertions compiled with -source 8 and run: the production
NPE and the message that replaces it; both unprefixed-key paths and their
precedence; the doc-id translation and its failure; an accented byte decoding
correctly under windows-1252; an invalid byte failing with an actionable
message and the REPLACE escape letting it through; trailing empty fields,
shown beside what the legacy split would have returned for the same line; the
BOM; the same line parsed with quoting on and off; and the pre-scan over
several files including the capped listing, the empty-content-value case, the
malformed-row-not-double-counted rule and the traversal. The codebase rule
scans run clean on the new package: no family literal, no charset-less
getBytes, no FileWriter or FileReader, no platform-default OutputStreamWriter,
no ofPattern containing DD.

One note on those scans. The naive version flagged CLICT and FileReader, both
inside javadoc explaining the legacy defects. The scan now strips comments
before matching, which is worth carrying over to the other build checks - a
rule that fires on its own documentation trains people to ignore it.
