ftpsend, batch 0: specification, and UAT decided two of the rules

Specification only. No code, no dependency, no registration.

A new internal executor ftpsend that uploads the files of a packaging
directory to an FTPS server over an explicit TLS control channel,
authenticating with a client certificate in a PKCS#12 file. It replaces
scripts/Send-FTPS.ps1, which has never been more than a skeleton that sleeps
two seconds and returns 0, and the external FTPS.exe invocation used for the
z/OS deliveries.

The batch-0 question was which of the five files in 40_PACKAGING are sent and
in what order. The answer is that the executor must not know: file sets differ
per feed and completion semantics belong to the receiving system. The step
carries an ordered list of DOS/UNIX masks (* and ? only), edited with ADD and
DELETE and reordered with UP and DOWN, as repeated <send> elements the way
<replacement> and <reportQuery> already are. Order is masks in list order,
then files sorted by name - the sort is explicit, because directory
enumeration is name order on NTFS and hash order on ext4, which was measured
during the tiffcompress work. First match wins, so a trailing catch-all does
not duplicate the .tar. A mask matching nothing fails the step unless marked
optional. The first failure aborts everything after it, not configurable,
because that is what makes the ordering mean anything: if the .tar fails, the
.control that announces the package as complete must not follow it. The whole
ordered plan is logged before the first byte moves.

Two rules come from a UAT session rather than from design. Against gbwu2719685
the control channel completes in full - TLS up, client certificate accepted -
and the data channel does not open: LIST fails, the server answers 227 with an
unroutable 10.117.145.81, and a 49 KB .tar transfers 0 bytes. First, the
client is not the problem and no client-side option fixes it - the working
client already reuses the TLS session and already substitutes the passive
address, which are the two behaviours this specification requires, and it
fails anyway. That is recorded so the first failing run is not searched for in
the code. Second, a remote file existing proves nothing: the 0 KB .control
appeared to arrive, and a second attempt reported it already present, which
looked like success and was not, because servers create the destination file
on accepting STOR, before a byte crosses the data channel.

Hence the verification rule: after each file, SIZE on the remote name, and it
must EQUAL the local byte count. Not greater than zero - that rejects the
.control, which legitimately weighs zero bytes. Not absent - that accepts a 49
KB .tar that arrived empty. Only equality separates the two. SIZE travels on
the control channel, so it works where the data channel is unreliable and
where listing is refused. The executor never sends LIST, NLST or MLSD at all.

Transport is a JDK-only client in a Spring-free package behind an
FtpsTransport seam, for the reason that shaped json2csv: Maven Central is
unreachable from the sandbox, so a commons-net implementation could not be
compiled here, let alone exercised, and would arrive on the target having
never run. Scope is STOR to two known servers over explicit TLS, passive.
commons-net stays as the fallback behind the seam.

ignorePasvAddress and reuseTlsSession default to ON, departing from the rule
that a new behaviour is born off. A default known to be wrong for both servers
in scope is not conservative, it is broken. Both stay switchable per target.
