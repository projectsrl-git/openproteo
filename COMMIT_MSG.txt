A save reloads the saved workflow, not every workflow

Every save called WorkflowRegistry.reload(): each *.xml parsed again,
each feed's directories re-created, one WORKFLOW_LOADED appended to the
audit trail of EVERY feed, every cron timer cancelled and re-created.
None of it was needed for the workflows that had not changed.

WorkflowRegistry.refresh(names) reads the files the caller wrote, plus
any *.xml whose modification time or size differs from when it was last
read (so a file dropped in by hand is still picked up by the next save).
Contract: the registry ends up exactly as reload() would leave it - same
workflows, same order, same load errors. Where that depends on the whole
directory (a feedId declared by two files or moving between files, a
set-up failure to retry, a directory not listed) refresh calls reload()
and logs why. WorkflowScheduler.reschedule(Refresh) re-plans only what
was loaded or removed.

Callers moved: designer save, save-xml, Variables mass save, lock,
delete. Not moved: /api/reload, start-up, Bulk, Import.

Visible difference: the audit trail of a feed no longer receives
WORKFLOW_LOADED when another feed is saved. No feed output changes.
No new runtime parameter (checklist 10), hence no switch: stated as a
judgement call in the session note.

Limit: a file changed by hand that keeps both its modification time and
its size is not noticed by a save; Reload XML definitions notices it.

Found, not touched: delete never rescheduled, so a deleted scheduled
workflow keeps a timer that fails at each firing until the next
reschedule.

CLAUDE.md: the rule for callers (refresh with the file names, then
reschedule with its result). USAGE.md: "What a save reloads". Kit in
tools/registry-refresh-test. README.md not touched.

Verified on Linux (sandbox, ext4; Temurin 1.8.0_432 compile and run,
OpenJDK 21.0.12 run; root and uid 65534; LANG unset and C.UTF-8): the
real WorkflowRegistry, WorkflowScheduler, WorkflowXmlParser and
FeedLayout against stubs for Spring, slf4j and AuditLogger; after every
refresh the registry and the scheduler compared with a fresh reload of
the same directory - 8 groups, random walk of 600 rounds on 6 seeds, 0
failures; 19 mutations on copies, all killed, a 20th investigated and
the unreachable clause removed; ApiController by differential compile
with two positive controls; USAGE.md through the real render().

Verified on Windows: nothing. Read, not run: File.compareTo ignoring
case, NTFS timestamps, on-disk name case differing from the caller's.

Verified on neither: the Maven build, Spring wiring, the five endpoints
over HTTP, the real AuditLogger hash chain.
