elarxml: a disk guard that cuts the input where the run stopped

Asked for because it is not hypothetical: the output disk fills regularly and
the repair afterwards is done by hand.

Filling it mid-INDX is not a clean failure. That batch aborts and nothing of
it goes out, but the batches before it have reached their final names and are
on the share, while the input still carries its own name. The next run
therefore reads it from the top and delivers those documents a second time,
which is why the CSV has been split by hand first.

Under batchBy=BYTES, before each new INDX is opened, the free space on the
output directory is checked against twice maxBytesPerBatch plus a tenth.
Between batches is the only place where the question of which rows are done
has one answer: every INDX opened so far has reached its final name, so the
rows before this one are delivered and this one is not. A check inside a batch
would have to answer it holding a half-written file.

When the space is not there the run stops before the file exists and the input
becomes three. The original is kept as .failed, renamed and otherwise
untouched, so what arrived survives as it arrived. The rows already dealt with
go to .done_before_failure, deliberately not a .csv so no later run picks it
up. Everything from the row that was not processed goes to .remaining.csv,
which the next run reads as an ordinary input with nothing to rename by hand.

The invariant that makes it trustworthy is checked rather than assumed: the
rows of the two halves add up to the rows of the original, exactly, and a
mismatch fails with nothing renamed instead of leaving a split nobody can
reconcile. The rename comes last, so a failure while writing leaves the
original under its own name. The discards file for the delivered part is
published, because that part really was delivered, unlike an aborted run where
it would be an account of nothing.

The input is re-read to produce the two halves rather than buffered as it went
by. A million-row CSV would be a couple of hundred megabytes held for a case
that almost never happens, on the exact path where the machine has just run
out of resources.

The guard does nothing under batchBy=DOCUMENTS, where there is no size to
reason from, and nothing when the filesystem returns zero for its free space,
since refusing every run on a share that will not answer would be worse than
not checking. checkFreeDisk=false turns it off.

VERIFIED
- 29 assertions for the guard, --release 8. The one that closes the loop: a
  run cut short by the disk, then a second run over the remainder, and 20
  documents delivered exactly once between the two with nothing renamed by
  hand. Plus the threshold arithmetic; that ample space changes nothing; the
  three files and their contents; that the halves add up, are disjoint and
  preserve the original order, and that both carry the header; that the
  delivered half is not a .csv; and that neither DOCUMENTS batching nor an
  unreportable filesystem stops a run.
- The free-space figure is the one thing behind a seam. A disk cannot be
  filled on demand in a test, and a safeguard never seen to fire is not a
  safeguard, so the figure is injected and everything built on it is exercised
  for real.
- 108 designer assertions, up from 106, the new ones covering the guard's own
  field.
- 144 IFS store assertions, the end-to-end identity between a local and an IFS
  delivery still byte for byte, all six elar suites and the elarcheck panel
  unchanged, scans clean.
- A defect caught by the panel suite rather than by review: the first
  insertion of the guard's checkbox left an extra closing div, and the
  malformed HTML silently truncated everything after it in the panel - the
  whole content-source subsection vanished and nine assertions fired. An
  unbalanced tag in a string-built panel does not throw; it eats the rest.

NOT VERIFIED
- mvn clean package: Maven Central is unreachable from the chat sandbox, so
  the build on the target machine remains the only final proof. The elar
  package compiles and runs standalone in full; the one line added to
  runElarXml cannot be compiled here, since the engine package needs Spring
  from the internal Nexus.
