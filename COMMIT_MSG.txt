build_openproteo.sh: resolve the project from the script location, not the git top level

The script assumed the git top level was the project and moved there, so on a checkout where the
repository root sits above the project -- /projects/devpodtest as the repository and
/projects/devpodtest/openproteo holding the pom -- it left the project directory and failed with
"pom.xml not found in /projects/devpodtest".

The project is now the directory that contains pom.xml, looked up in order: the parent of the script's
own directory (the script lives in <project>/scripts/, with symlinks resolved), then the current
directory, then the git top level; if none matches, the error lists all three. The script reports the
project directory and, when the repository root differs, prints a note so the nesting is visible instead
of surprising. Staging happens after changing into the project, so in a parent repository only the
project subtree is committed and files elsewhere in the repository are left alone.

Two further robustness fixes. Starting it as `sh script.sh` runs it under dash, where `set -o pipefail`
does not exist, so it now re-execs itself with bash when BASH_VERSION is unset. And git is required only
to commit, push and stamp the version: on a plain source copy with no repository, `-b` still builds and
says the WAR will carry no commit or build number, while committing is refused with a clear message.

Docs: .claude/2026-08-02-build-script-project-resolution.md and CLAUDE.md.

Verify: exercised against a stubbed mvn in throwaway repositories reproducing the reported layout --
the project nested in a parent repo invoked with `sh` (works and notes the nesting), invoked from
another directory by absolute path, a commit in the parent repo (only the project subtree staged, a
file outside it stayed untracked), invocation through a symlink, and a non-git directory (build only
works, commit refused). Checked with bash -n.
