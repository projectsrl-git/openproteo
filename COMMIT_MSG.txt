XML viewer: a real table view, replacing the indented tree

The previous batch rendered an indented tree with attributes written inline as
name=value. That was the wrong shape for the request, so it is replaced rather
than extended.

An .xml file now shows its data as tables. A single element becomes a titled
block with an Attribute | Value table: the attribute name in one cell, its
value in the cell beside it. A run of consecutive sibling elements that share
a tag becomes ONE table with a header, its columns being the union of their
attribute names in first-seen order, one numbered row per element, plus a
value column when any of them carries text - which is what a list of <var>,
<step> or <Obs> actually is. An attribute that a given row does not have is
drawn as a hatched cell rather than left blank, so "absent" is visibly
different from "present but empty". A row whose element has children of its
own gets a toggle that opens that element's own block in a full-width sub-row
inside the table. Runs are consecutive only, so document order is never
rearranged to make a nicer table.

Expand all and Collapse all work on the whole document, and one search box
matches tag names, attribute names, attribute values and text content at once,
with highlighting; branches with no match are dropped and the path to every
match is kept and opened, so a hit is never buried inside a closed element.

There is also an architecture change behind it. The document is walked once
into a small model - references plus a lowercase haystack per element - and
the tables are rendered from that model on demand rather than built in full up
front. The file this was reported against is 1.16 MB and 4522 elements, which
is not a size at which building every cell eagerly is reasonable. Because the
search runs on the model and not on the DOM, it still finds matches inside
branches that have never been drawn, which a purely lazy DOM approach could
not do.

Every colour is an existing theme variable, checked to resolve in the light
block as well, so both themes stay legible. The standalone xml_viewer.html in
the repository root gets exactly the same renderer - it is written once and
injected into both files - with browse, drag-drop, its own theme toggle and
zero external references.

Verified with jsdom against a realistic workflow XML: 30 assertions, all
passing. Run grouping puts three <var> siblings into one run and two <step>
siblings into another; the column union is taken in first-seen order and keeps
an attribute that only one element has; key and value come out as separate
cells; the header row is exactly the expected columns; there is one row per
element with the missing attribute rendered as the hatched cell; a row with
children expands into a sub-row whose nested query text and nested attributes
are present; collapse and expand work on the whole document; and search
matches an attribute value, a tag name and text content, is case-insensitive,
drops unrelated branches while keeping the path to the match, reports no
match, and restores everything including removing the highlights when cleared.
One assertion exists purely to stop the old shape returning: no inline
name=value text and no xt-attr class may appear anywhere in the output.

node --check passes on viewer.js and on the standalone page, both with zero
literal newline/CR escape sequences and no external references.
