elarcheck: the INDX validation executor, implemented

Batches 1 to 7 of .claude/ELAR_CHECK_EXECUTOR.md in one pass. The executor
inspects delivered ELAR INDX files and reports every defect that has caused a
real rejection, before the files are sent.

The package is free of Spring and of the orchestrator's own types, so the
whole checker runs against real files in a test rather than only on deploy.
Two classes carry it - one for findings, counters and the verdict, one for the
two passes and the run - and the method in InternalSteps only translates
parameters in and counters out, writing the findings file into the step
directory.

Read-only is verified rather than promised. The scan finds no
FileOutputStream, no Files.write or Files.delete, no renameTo, no
createNewFile, no FileWriter and no delete call anywhere in the package, and a
test asserts that the inspected directory's file list and modification times
are unchanged after a run. That property is what makes it safe to point at a
live delivery folder at any moment.

There are two physical passes per file. The textual one needs physical lines
and must keep going after the document stops being well-formed, which is the
whole point of reporting every malformed tag opener when the parser stops at
the first; the structural one needs the parser. StAX coalescing is off,
because with it on a payload of tens of megabytes would be materialised as a
single string - the exact accumulation that killed the legacy generator. The
value-break check therefore tests each character fragment rather than
assembling the value, which is equally sensitive and costs no memory.

Two defects came out of the tests.

The function that computes the next name for a resubmission searched for the
counter from the left. A real name is
RZ2.ELA.FTP.CLICT@DT.D26229.INDX.C152100.xml, so the first dot-C is inside the
family name: the search found CLICT and returned the name unchanged, silently,
which is the worst way for that particular function to be wrong. It now scans
from the right for a dot-C followed by exactly six digits. It was caught only
because the test used the real family name rather than a toy one.

And the counter advances by one second rather than by the generator's sixty.
Sixty would land exactly on the next batch's name, which is the one name in
the directory guaranteed to be taken; one second is the smallest change that
makes a name unique and cannot collide with a sibling batch. The assertion
that found this was mine and was wrong - it expected a minute - but the answer
it forced is the right one and is now recorded in the code.

Verified with 63 assertions on the checker and 15 on the adapter, compiled
with --release 8 and run against purpose-built files. The one that matters
most: a line break inside a value gives a CORRUPTED verdict while
well-formedness passes, reported at the line where the break starts and
carrying the record ordinal. That is the distinction a naive checker gets
wrong, and such a file is accepted by ELAR and archived with a wrong value in
it while nothing downstream ever flags it. Also covered: twenty wrapped
payload lines producing no findings at all; a markup break reported as a
different kind from a value break, because the repairs differ; a malformed
opener caught by both passes independently, with the parse error stating that
the textual checks still covered the whole file; the two line-length findings
with their distinct messages, one that would still arrive and one that loses
its closing tag; missing, duplicate and empty as three separate findings
across four records; both pair failures and a correct pair; the hash check off
and on, catching exactly the wrong document; no field value anywhere in the
findings file or the log; the cap holding while the counters stay exact; the
counters reaching run.vars; and the inspected directory unchanged.

USAGE.md was verified by running the docs renderer's own render function
against the real file: twenty paragraphs in the new section, none of them a
sentence fragment, and no raw markdown outside the code blocks.

NOT verified, and these are the honest limits. mvn clean package:
InternalSteps, the parser, WorkflowEngine and designer.html need the Spring
tree from the internal Nexus and were checked structurally instead. And
nothing has run against a real INDX - the definition of done requires the
reported line and record numbers to match what ELAR reported, and that needs
the known-bad file together with its rejection report. The designer has the
dropdown entry but no configuration panel, the same gap elarxml has; until one
exists, configure the step with plus-param entries, and only inputDir is
required.
