elarxml IFS content batch 3: the wiring, and two batch-0 predictions undone

contentSource (LOCAL by default, or IFS), contentIfsPath and
contentIfsMaxListing on the step; runElarXml builds an IfsContentStore over a
Jt400Ifs from the step's datasource when the source is IFS; a subsection for

TWO CLAIMS FROM BATCH 0 WERE WRONG, BOTH IN THE SAME DIRECTION

buildXml needed no change. It already emits datasource in the generic run of
step attributes, beside script and exec. And the parser needed no change
either: WorkflowXmlParser reads datasource unconditionally for every step
rather than per executor kind, so an elarxml step already carried it.

Worth recording because the reasoning that produced both was plausible and
still wrong. I inferred from "this is an attribute, not a param" that the
emission must be per-executor, without reading the emission. The reportQuery
comparison was the wrong one: that was a new child element, which nothing
emitted, whereas an attribute that already exists for other executors is
emitted for this one too, for free. The param-versus-attribute distinction was
real; the conclusion drawn from it was not.

A LEAK THE BATCH 1 SEAM DID NOT COVER

ElarRun closes the store on every path IT REACHES, but it validates the
configuration before entering that try/finally - a missing idms.namespace, say
- and an exception from there returns without ever releasing the connection.
runElarXml now closes the store in a finally of its own: whoever constructs it
closes it too, and close() is idempotent so the two do not fight.

This is the second instance of the same lesson in three batches. A Closeable
is a claim, and every path out has to honour it, including the ones that leave
before the owner's try block is entered.

SETTINGS THAT CANNOT TAKE EFFECT ARE REFUSED, NOT IGNORED

contentIfsPath set while contentSource is LOCAL fails validation in the
designer and is reported in the step log at run time, rather than sitting in
the workflow XML looking effective. An unrecognised contentSource fails the
step naming the value instead of falling back to a default.

  the file name is used; IFS without a datasource is refused; buildXml carries

  closing twice neither logs the summary twice nor disconnects twice.

  local disk and from the IFS store give a byte-for-byte identical INDX, same

- All six elar suites and the elarcheck panel suite unchanged. Template scans
  clean.
