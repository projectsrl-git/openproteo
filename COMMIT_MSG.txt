audit_report.md: a per-run evidence report

Writes a single Markdown document per successful run at
{feedDir}/_logs/runs/{runId}/audit_report.md, next to that run's step logs:
the workflow's output data as Operations shows it, and one paragraph per step
with its timestamps, its variables and its standard output.

The finding that made the "also for past runs" part feasible: run.vars looks
like a flat map with no record of which step produced what, but
WorkflowEngine:947-951 writes BOTH forms on every step output - the plain name
and the namespaced stepId.var. Per-step attribution is therefore already in
the persisted run JSON, so no audit-trail replay and no parsing of step logs
is needed to document a run that happened months ago. A run whose vars carry
no stepId. key predates that recording and gets an explicit note saying the
per-step breakdown is unavailable, rather than an empty section that would
read as "this step produced nothing".

Two different sets of variables, deliberately kept apart because the request
named both. The Output data section is the list the workflow DECLARES -
outputData.<var> step params plus the workflow-level ones - which is exactly
what the Operations grid shows in its "output data" column;
declaredOutputVars(def) was extracted out of the feeds endpoint rather than
duplicated, so the report and the column are the same code path by
construction and cannot drift. A declared variable the run never produced
appears with an empty value instead of being dropped, so the reader can see it
was expected. The per-step tables are the separate matter of what each step
actually published.

Each step paragraph carries status, exit code, attempts, start and end
timestamp with the duration computed between them, its validate checks when it
has any, the variables it published, and its standard output - the same lines
the run page shows when you click open on a step, so for a sql step the
executed query is in the report. Gates are merged into the same chronological
sequence with their condition, outcome and who decided: a report that silently
dropped the approval step would not be evidence. A long log is shortened to
its first 100 and last 400 lines with the omission marked, keeping the head
rather than taking the pure tail the run page takes, because the query, the
datasource and the parameters are printed at the START of a step log and a
tail would cut exactly what the report is for. A fence inside a log is
neutralised so it cannot close the block and turn the rest of the log into
Markdown.

Generated on request only, never on run completion and never by a scan at
startup. POST /api/runs/{feedId}/{runId}/audit-report writes one run, from a
button beside the "open" link in Run history that appears only on a SUCCESS
run. POST /api/workflows/{feedId}/audit-report/last writes the last run of one
feed and is driven by the new "Audit report (last run)" button in the
Operations multi-select bar, which loops it over the selected feeds and
reports how many were skipped. Only SUCCESS runs are accepted and test runs
are excluded: a failed run's evidence is its log and its audit trail, and
calling a document for it a report invites it being read as a delivery record.
Re-running overwrites, so both are safe to repeat.

One limitation is stated in the report itself, in the docs and in the spec
rather than left to be discovered: the declared output-data list is the
definition AS IT IS NOW, so for an old run a variable added since will show
empty and one removed since will not appear at all. The definition of the day
is not kept alongside the run, so this cannot be fixed for history - it is
precisely what workflow versions exist to avoid going forward.

New engine/RunAuditReport is free of Spring and of any IO, everything it needs
being passed in, so the rendering compiles and runs on its own. No new
dependency; Java 8.

Verified. RunAuditReport compiled standalone with -source 8 against the real
run model and exercised by 34 assertions, all passing: the header and the
computed run duration; the Output data section including a declared variable
the run never produced showing empty rather than dropped; steps numbered in
order with a gate placed chronologically between them; per-step start and end
timestamps and duration; per-step variables, with a grandchild key correctly
NOT listed as a step variable and the plain non-namespaced feedId correctly
