feed schema index batch 1: the tool, and an XML trap that read nothing

tools/Get-FeedSchemaIndex.ps1: one read-only PowerShell script writing a
CSV census of the record layout of every feed OpenProteo loads, one row
per field, joining the workflow XML with dataschema.json and
displayschema.json. Nothing under src/ is touched, so no feed can change
behaviour; no build, no WAR, no restart. 150 assertions and 14
mutations, all caught. Spec updated at .claude/FEED_SCHEMA_INDEX.md.

The defect that mattered was invisible to review. PowerShell's XmlNode
adapter exposes attributes and child elements AS properties, so
$root.Name on <workflow name="Feed A"> returns "Feed A" and not
"workflow". Every workflow was therefore rejected as "expected root
element <workflow>, found <Feed A>", the index came out empty, and the
message read like a malformed file rather than like a bug in the reader.
Every XML access now goes through the .NET getters, which a document's
own content cannot shadow.

The first real run found a second one, in usage rather than logic. Under
pwsh -File every argument is a plain string and a comma is not an array
separator, so -Variables 'a:x','b:y','c:z' collapsed into a single
column whose header was the rest of the command line. Silent; the only
symptom is a header nobody reads twice. Such an entry is now split, but
only when the split is unambiguous - every part must look like a
variable name and the parts must agree about carrying a description - so
a description that merely contains a comma survives verbatim. Splitting
that would be the quiet corruption the rule exists to prevent.

Mandatory fields are carried twice on purpose. field_nullable follows
InternalSteps exactly, asymmetry included: mandatory only for the
boolean false or the string "false", so an absent attribute, a 0 and a
typo all mean nullable. The displayschema carries its own Nullable and
the two disagree on three of ten columns in this repository's own
shipped samples, so display_nullable sits beside it, both are written,
and nullable_disagreements counts the difference. The dataschema is the
authority because it is what the validate step acts on; reporting one
column alone would give a clean answer to a question the two files do
not agree about.

Two harness defects were exposed by the same run, both of the class that
reports success: the fixture declared [string]$DataJson, and
[string]$null is the empty string, so "this feed has no displayschema"
wrote an empty one; and the alias-agreement lift matched the first
occurrence of the chain shape in InternalSteps, which belongs to the
mask executor, so it compared the reader against the wrong Java and
reported agreement. Both fixed and both now anchored.

NOT VERIFIED: Windows PowerShell 5.1. The sandbox has PowerShell 7.4.6
for Linux, so the dialect is asserted by six scans each with a positive
control proving the scan can fire - a syntax argument, not a run. Nor
the real estate: the smoke run is this repository's own 15 workflow XML
files with samples/ copied into three feed directories, not 144 feeds.
mvn clean package is unaffected; nothing here is in the WAR.
