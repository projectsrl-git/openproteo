Data sources: the same dead Edit button, found before it was reported

The FTPS targets page had its row buttons serialise the whole record into the
onclick attribute, and an apostrophe in a path killed them. That commit noted
this page carries the same pattern and left it alone because nobody had hit
it. Fixing it now, and it is not hypothetical: the field most likely to carry
an apostrophe here is the test query, because a SQL statement normally
contains a string literal.

Both row buttons now name a connection by INDEX into the loaded list. Nothing
else changes: same columns, same handlers, same endpoints.

VERIFIED
- The defect is reproduced first, against the page as it was: with a test
  query reading SELECT 1 FROM SYSIBM.SYSDUMMY1 WHERE 'a' = 'a', clicking Edit
  raises "Invalid or unexpected token" and leaves the form empty. 8 of 16
  assertions fail. After the change all 16 pass.
- The fixture carries two connections, not one, so a button resolving to index
  0 would open or delete the wrong record: the second row is the one edited
  and the one deleted. The lesson is now three pages old - an assertion proves
  nothing about an index when there is only one thing to index.
- Every row button is asserted to match editAt(n) or delAt(n) exactly.
- 5 mutations, 5 caught: each of editAt and delAt ignoring its index, delAt
  not resolving the id, the list not being kept, and the payload put back into
  the attribute.

NOT VERIFIED
- mvn clean package, unchanged. This commit touches one template and no Java.
- Whether any connection in use actually carries an apostrophe today. The fix
  does not depend on it.
