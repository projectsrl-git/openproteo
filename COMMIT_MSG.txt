Copy file list: the CSV reader extracted and shared (batch 1)

Gate 0 of .claude/COPY_FILE_LIST.md is answered and recorded in the spec,
with the one reversal struck through rather than rewritten: with a list the
step may only COPY, so filecopy's move and list modes will be refused in
batch 2 rather than ignored. ifscopy is finished as it stands, the column
holds bare names or complete paths decided per value, and the destination is
one flat directory.

This batch is the extraction and nothing else. engine/CopyListSupport, JDK
only and free of Spring, JTOpen and the orchestrator's own types, absorbs
engine/IfsListSupport, which is deleted; runIfsCopyList is its one call site
and asks for Flavour.IFS. The LOCAL flavour exists and is tested but nothing
calls it yet: no executor gains a parameter, no template changes, and no
feed can behave differently. A facade keeping the old name was rejected - it
would claim only ifscopy uses the class, which is the opposite of why it was
extracted.

Exactly one rule differs between the two flavours: how a base and a listed
name are joined, and therefore what the file is called in the destination.

Paths.get(name).isAbsolute() is NOT the local test. On Windows
Paths.get("/logs/x.pdf").isAbsolute() is false, because a leading slash
there means the root of the CURRENT drive - and that is exactly the shape a
list produced by an earlier ifscopy step carries, so it would have been
joined under the source directory. The rule is an explicit first-character
test for / or \ (which also covers UNC), then an explicit drive-letter test,
with Paths consulted only as a last net. A drive-qualified name with no
separator is treated as complete: it is relative to that drive, not to ours.
The join separator follows the base, falling back to the platform's, because
a fixed character produces D:\landing\in/x.pdf - which works and reads as a
mistake in every log line that quotes it.

Verified:

* THE NO-OP IS MEASURED, not asserted. The pre-patch IfsListSupport taken
  out of f900d99 and the post-patch CopyListSupport compiled side by side
  and run over the same corpus, comparing every field of ListResult plus
  join, localName and MAX_REPORTED: 22018 cases, 0 mismatches. The corpus
  crosses 16 files against 3 charsets, 2 delimiters, header and no header,
  13 column specifications and 10 bases, and includes quoting, a BOM on the
  header and on a first data row, ISO-8859-1, degenerate files and two files
  of 130 rows that push past the 50-line reporting cap in both directions.

* Fourteen mutations, all caught, each applied by a runner that asserts its
  anchor is present before editing. Two came back green and neither was a
  pass: one anchor never matched, and one was a real corpus gap - no file
  held a whitespace-only line. Added, together with a delimiters-only line,
  which is the opposite case and must stay a row. That mutation now fails by
  900 mismatches.

* Every LOCAL mutation leaves the differential suite green. Breaking the new
  flavour cannot change what ifscopy does, which makes the inertness a
  property of the structure rather than of my care.

* 52 assertions on LOCAL, which has no predecessor to be compared against,
  including one real read where the base falls back, a rooted name ignores
  it, a duplicate collapses, a blank is counted with its line number and the
  collision guard fires - with the same list read as IFS reporting no
  collision, because there the two names differ. An unexpected throw in that
  suite is now a failure rather than a stack trace that stops the report.

* javac --release 8 on both classes; brace, parenthesis and bracket balance
  on InternalSteps.java with strings and comments stripped; by reflection,
  every ListResult member runIfsCopyList touches exists on the new class and
  the seven-argument read signature matches the call; and the class in this
  patch is byte-identical to the one the suites ran against, compared by
  SHA-256.

Not verified: mvn clean package, and InternalSteps.java itself, which needs
the Spring tree from the internal Nexus. CopyListSupport is in the same
package, so the change adds no import. Not reproducible here either: the
Windows half of the isCompleteLocal rule, since on Linux
Paths.get("/logs/x.pdf").isAbsolute() is already true and the case the rule
exists for cannot be made to fail. The mutations do prove the explicit test
is load-bearing for \logs, UNC and D:\ - for the leading slash on Windows
the argument is the documented semantics of Paths, not a measurement.
