elarxml batch 2: streaming writer, template model, atomic output

The writer, and with it the decision that shapes the rest of the executor.

WrappingXmlOut owns where a line may break, and it is driven by the emitter
rather than by a stream underneath it. A Writer that counts characters and
inserts a break every N cannot know whether it is inside markup or inside a
text node, which is the legacy defect restated rather than fixed: IndxBuilder
serialized the document to a String and chopped it at blind offsets. That
survived for a reason worth recording in the code, and it is: at twenty-five
thousand characters a line and payloads of megabytes, essentially every break
landed inside the Base64 of the content tag, where whitespace is ignored by
any decoder. A metadata value straddling a boundary would have been silently
corrupted and nothing downstream would have flagged it.

So the rule is positional. Between elements and between attributes a break is
always legal; inside a Base64 payload it is legal at any multiple of four;
inside any other text node it is never legal, and a value that cannot fit a
line of its own fails naming the tag rather than being split or letting the
line over-run. The XML declaration is generated from the output charset and
never copied from the template, which is what actually closes the defect where
delivered files declare ISO-8859-1 while being written with the platform
default. A value that cannot be represented in the output charset fails naming
the tag and the code point, checked per value with canEncode so that the
message can name the tag, with REPORT on the writer itself as the backstop.

IndxTemplate discovers the model instead of assuming it, since every family
has its own template with its own tags and only one has been read. The
container is found by namespace and local name, both from the properties; it
must hold exactly one element child, which becomes the per-document block
whatever it is called; everything before and after is emitted verbatim. Any
other shape fails at parse naming what was looked for and what was found,
before any output exists. Because the block is walked as parsed, a family's
constants survive on their own and a row value overrides them where one
exists. unknownMappedTags reports a mapping that names a tag the template does
not contain, which would otherwise be a silent no-op.

AtomicOutput writes to a .part file in the same directory, so the rename stays
on one volume and is atomic, and renames only after a clean close. An existing
final name is refused unless overwriteExisting is set. close aborts unless
commit succeeded, so every failure path leaves no deliverable - the legacy OOM
left a 0 KB INDX beside three complete files, indistinguishable to anything
downstream from a success.

Verified with 46 assertions compiled with --release 8. The load-bearing ones
concern the wrapping: no line exceeds the maximum, every full payload line is
a whole number of quads, no line ends inside a tag, and the payload is
byte-identical to what was written once the breaks are stripped. Then the
declaration following the charset parameter rather than the template;
constants surviving while a row value overrides, BU included since it is both;
escaping in text and in attributes; the over-long value refused by name; the
euro sign refused in ISO-8859-1 and accepted under the documented windows-1252
escape hatch; three malformed templates refused with actionable messages; a
family with entirely different tag names working unchanged; and the atomic
file including that an aborted batch leaves neither a deliverable nor a temp.
End to end the produced file is re-read with its declared charset and the
accented byte on disk is 0xE9, so the declaration is proven against the bytes
rather than asserted.

The rule scans now also assert the absence of StringWriter,
ByteArrayOutputStream and Transformer or DOMSource. Those are the three
vehicles of the legacy OutOfMemoryError, and they are gone by construction
rather than by discipline.

Two notes on the environment. The sandbox had no JDK this session, only a JRE,
so one was installed and everything was compiled with --release 8 - stronger
than the earlier batches' -source 8 -target 8, because it also checks the API
surface rather than only the language level. And the container reset mid-turn,
taking the working clone with it; recovery was to re-clone and re-apply from
the zip already delivered, which is an argument for delivering often.
