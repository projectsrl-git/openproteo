Copy file list: the designer panels for filecopy and safecopy (batch 3)

Makes the option reachable. Batch 2 delivered the engine and until now
nobody could configure it through the interface at all.

Both executors get the Files to copy switch, the same one ifscopy has,
wired through copySetListSource - which stores the value AND redraws. The
panels show different fields in the two shapes, so a select that only
stored the value would leave the page contradicting itself: that is the
defect already recorded for contentSource and for batchBy. One
copyListFields builder serves both panels, for the reason the reader itself
is shared: two copies drift.

In the list shape the source field is relabelled rather than hidden - that
fallback IS the "directory + file name from the CSV" combination and should
be visible where it operates - the pattern is hidden, and clientValidate
stops demanding source while requiring dest and both CSV fields, reporting
both missing ones rather than the first.

filecopy's Mode field stays VISIBLE under a list, with the panel saying in
red that only copy is allowed. The executor refuses the other two rather
than ignoring them, so hiding the field would leave a stored move
uncorrectable. clientValidate refuses it at save as well.

buildXml, the parser, the writer, the DTO and PARAM_OPTIONS needed no
change: every field is a <param>, and variables.html already carries
listSource, hasHeader, onMissingFile and onNameCollision with these very
defaults. Asserted, not assumed.

Verified:

* 88 jsdom assertions against the real template; the same suite scores 36
  passed, 48 failed against the pre-patch one. The DOM is built FROM the
  real template with its scripts stripped, so every id the page bootstraps
  against exists by construction. Controls are driven by evaluating their
  own onchange ATTRIBUTE with `this` bound, as a browser does - jsdom does
  not run inline handlers, and calling the helper directly would supply the
  very step the page is meant to take.

* Structure is asserted by NESTING, not by presence. An unbalanced tag does
  not throw, it re-parents what follows, so an escaped subsection is still
  findable from the document and an innerHTML string test would pass. The
  stray-</div> mutation came back GREEN against the first version of that
  assertion, which is why it is written this way.

* 13 mutations, all caught: twelve by the panel suite, one - a literal
  escape sequence introduced into the JS - by the build checks.

Three things the run found and review would not have:

* A mutation runner piped into `head` left the tree mutated: SIGPIPE killed
  it before its restore. My check that the tree was clean, a grep for the
  condition, MATCHED A DIFFERENT LINE and reported all-clear. Restore is now
  in atexit and each line is flushed. A check that finds a match is not a
  check that found the right match.

* An anchor occurred twice again - the Delimiter field line is identical in
  ifscopy's branch - so the runner now refuses a non-unique anchor outright
  instead of silently taking the first.

* One green mutation was a genuinely bad mutation rather than a gap:
  dropping ` selected` changes nothing, because the browser selects the
  first option and fail is first. Replaced by reordering the options.

tools/scan_panel_redraw.js is also touched. It reported a clean run with
this control's redraw removed, and the reason is structural: it is keyed on
the PARAMETER NAME, and listSource is also written by ifsSetListSource,
which still redraws - one broken helper hiding behind another executor's
correct one. A second check was added, keyed on the helper, narrow enough
that it cannot cry wolf, still advisory. Its own first version matched
nothing at all, requiring a newline before the closing brace while every one
of these helpers is a single line - the exact property the file exists to
check for, occurring in the file itself. Proved to bite on all five helpers.

Not verified: mvn clean package; the UBS browser (flex with wrap throughout
and no new CSS variable, which is an argument and not a rendering); and the
panel's fetch calls, since rendering is exercised and the network is not.
