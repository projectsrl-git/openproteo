objpack keeps no rows in memory; a step ending with an Error is ended

On AIX, objpack on 100 000 rows (52 MB) stopped at "read 63271 rows"
and the step stayed RUNNING for an hour and a half.

Reproduced on Java 8: it kept every row as a map of its cells for the
whole run, which does not fit in 512 MB. And an Error in a step was
caught by nothing: the run pool logged it and the step stayed RUNNING.

- ObjectPack keeps per row what the checks and the names need. The
  other columns are read again from the CSV where they are written:
  the metadata, the dataschema's not-nullable check, the discarded
  rows. The file is checked to be the one read the first time; if it
  changed the step stops and leaves no half-written metadata.
- AuditJson.write streams instead of building the text first.
- InternalSteps.run catches Error: exit 1, a message naming the heap
  for an out-of-memory. WorkflowEngine.executeStep has the same net.
- The Platform page shows the heap the steps can use.
- ObjectPack.glob: every include/exclude pattern with a literal
  character threw PatternSyntaxException. Fixed.
- USAGE: a file uploaded from the Files panels is NOT in the scripts
  directory, and the Script field resolves no variable, so an alias
  cannot be written there. It said the opposite. The pre-check
  template's description is corrected the same way.

Same 100 000 rows after the change: completes with a 144 MB heap (not
with 128); with 256 MB the outcome is identical to the old code's
with 1 GB. No parameter added. Input that worked gives what it gave.

Not done: the Script field still resolves no variable (decided); the
audit file is still read whole. Next intervention: the Delimiter
field as a variable, and a listing check in the pre-check script.

USAGE.md and the objpack and objunpack specs updated. README.md and
CLAUDE.md not touched.

Verified on Linux (sandbox; Temurin 1.8.0_432 and JDK 21.0.12;
LANG=C.UTF-8; root): ObjectPack old against new on 625 cases, the
whole outcome identical; 53 assertions on the new refusals; the real
InternalSteps.run, lifted, with a real OutOfMemoryError, 268
assertions; the Platform row in jsdom. A subset as uid 65534 and with
LANG empty. 34 mutations, all caught after three holes in the suite
were closed (spec section 18).

Verified on Windows: nothing.

Not verified on either: AIX and the IBM JVM, where a short heap may
take minutes to become an error; WorkflowEngine's new catch (the
class does not compile here: differential compile only); a browser;
mvn clean package.
