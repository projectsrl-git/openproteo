setvar: evaluate a chain of integer additions and subtractions

Reported from the field: an assignment of 74023 + 5164 - 12 wrote the
expression as text instead of the number. evalArithmetic handled exactly TWO
operands - it found the first " + ", then tried Long.parseLong on "5164 - 12",
failed, and returned the input unchanged. It now evaluates a chain of
whitespace-separated terms left to right, with no operator precedence: A + B -
C + D gives one number. Only + and - are evaluated; * and / are not, so there
is nothing to disagree about on precedence.

The space on each side of every operator is still required, and that was kept
deliberately rather than relaxed. It is the guard, not a formatting rule:
accepting A-B would make a literal like 2026-08-05 read as arithmetic and
silently become 2013, which is exactly the kind of regression that would go
unnoticed on an existing feed. With the space requirement, any value that has
no spaces - a path, a date, a ;-separated list - passes through untouched, and
so does anything that is not a chain of whole numbers, which is the normal
case for a setvar value.

One shape other than genuine chains does change and is declared rather than
hidden: "2026 - 08 - 05" WITH spaces around the hyphens now evaluates to 2013,
where the old code returned it as text. Nobody writes a date that way, and the
space is the documented signal for arithmetic, but it is the one difference
worth knowing about. An overflow returns the expression unchanged via
Math.addExact and subtractExact rather than a wrapped number: a wrong figure
in a reconciliation is worse than an unevaluated one.

Also documented, because it caused the original confusion: assignments within
ONE setvar step cannot refer to each other. Every parameter of a step is
resolved before the step runs, so a value computed from another assignment
needs a second setvar step. The designer label and the USAGE entry now say all
of this instead of the previous "simple A + B / A - B math", which was easy to
read as "simple arithmetic" rather than "exactly two operands".

Verified. The new evaluator was compiled with -source 8 and run against 29
assertions, all passing, alongside a transcription of the OLD implementation
so that every case can be compared directly. The reported expression now gives
79175 and the same expression without spaces is still returned as text. Chains
of three, four and six terms, mixed + and -, extra whitespace and tabs, a
negative first term, subtracting a negative and zero all evaluate. Left
untouched: a literal date in both the hyphen and slash forms, a Windows path,
a ;-separated list, plain text with spaces, non-numeric terms, a dangling
operator, an operator alone, multiplication, division, a mixed expression, a
single number, empty and null. Overflow returns the input. The
backward-compatibility block runs old and new side by side on eight
expressions that already worked and asserts they agree, so the only behaviour
changes are the chains themselves and the spaced-hyphen date noted above.
Brace and paren balance is 0/0 on InternalSteps, node --check passes on the
designer's inline JS with zero literal newline/CR escape sequences.
