ftpsend batch 4: the targets page, and a table the renderer cannot draw

The admin page for FTPS targets, its API, and the USAGE.md section. This
completes ftpsend: a target can now be created without editing JSON by hand.

The API grows save, delete and a test alongside the read that batch 3 added.
All three passwords - account, certificate, truststore - follow the rule the
datasources already use: the placeholder leaves the server if one is set and
nothing if none is, and a placeholder coming back means unchanged, so a save
cannot blank a password the page never held.

The test button connects, negotiates TLS, logs in and hangs up. It transfers
nothing and lists nothing, and the page says so in as many words next to the
green tick: it proves the control channel and proves nothing about the data
channel, which is the half that fails when a passive range is closed or a
balancer splits the two connections. The conversation is shown either way,
because when it fails the useful thing is which command it reached.

The page states the two measured facts where they are needed rather than in a
document nobody opens beside the form: that Windows-ROOT carries root CAs and
not intermediates, next to the trust selector, and that with TLS 1.3 available
the data channel will not reuse the control session, next to the version
selector.

VERIFIED
- 52 page assertions green in jsdom against the real template. Every control
  is driven by an event on the rendered element, and the save assertions read
  the request body the page actually sent rather than its variables: the
  placeholder going back untouched, an empty password staying empty, the port
  arriving as a number, the booleans as booleans.
- 13 page mutations, 13 caught, after two came back green and were
  investigated. One was malformed. The other was real and is the more
  interesting: New failing to clear the truststore password changed nothing,
  because no test had ever put a value in that field. Asserting a field is
  empty proves nothing when it was empty to begin with, so every field New
  clears is now filled first and then asserted.
- The USAGE.md section was rendered with the real render() from docs.html,
  extracted with its helpers and run over the file: 90 TOC entries against 81
  before, no Markdown leaking outside code blocks, and the new section
  present.
- The designer suite from batch 3 still passes, 42 assertions.
- Patch applied on a second clean clone at 93b6c6a, compared byte for byte,
  and the page suite re-run from the applied tree.

A defect avoided rather than found, worth recording because it was one grep
from shipping: the section was first written with a Markdown parameter table.
The renderer in docs.html has no table support at all - no table, td or th
anywhere in it - and USAGE.md had never contained one, so seven rows of pipe-
separated text would have rendered as seven stray paragraphs. The table is now
the bullet list every other Parameters section uses.

  so ApiController and PageController are not compiled anywhere. Both edits
  are mechanical, and they are the risk this commit carries alongside batch
  3's.
- The Thymeleaf render itself. The harness substitutes what the server emits
  for the one attribute the scripts read; the rest of the page is served as
  written.
- The test endpoint has never run against a real server. What it does against

  UAT host is the open question of section 2 and remains one.
- FtpTargetStore's JSON round-trip: Jackson is stubbed in the sandbox, so the
