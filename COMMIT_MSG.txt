Operations bulk bar: Continue/Stop, Delete feed vs run, delete guard

Adds bulk CONTINUE and STOP to the Operations drill-grid action bar, so a set
of paused feeds can be resumed or aborted in one go instead of one run at a
time, and disambiguates the DELETE button.

CONTINUE resumes the selected runs that are ON HOLD; STOP aborts the selected
RUNNING / QUEUED / WAITING_APPROVAL / ON_HOLD runs, which end as ABORTED. No
engine change was required to reach a held run: the ON HOLD suspend path only
removes the feed from runningFeeds, the run stays in activeRuns, and both
stop() and resumeHold() resolve by runId with a store.load fallback - so a
hold is reachable while the JVM is up and after a Tomcat restart. Treating
ON_HOLD as active in runningFeeds was deliberately rejected: it would
re-occupy the engine slot for a run that was parked on purpose.

The bar targets liveRunId || lastRunId. New WorkflowEngine.activeRunsByFeed()
snapshots the non-terminal runs still held in memory, including the ones that
released the slot, newest per feed and test runs excluded; ApiController
publishes it as liveRunId/liveStatus in the LIVE (non-cached) part of
/api/overview/feeds, because lastRunId is cached for 10s and would miss a run
started inside that window, while lastRunId still covers a hold orphaned by a
restart. Eligibility is filtered client-side and feeds with no actionable run
are reported as skipped; the endpoints stay authoritative, so a stale grid can
never act on the wrong run. PRODUCTION feeds require an explicit checkbox in
the confirm dialog, as for Clear history; this is UI-level only, since the
per-run /stop and /resume contracts are shared with the run page.

The bulk DELETE button posts to /api/workflows/{id}/delete, which removes the
WORKFLOW DEFINITION, not a run: it is relabelled "Delete feed" with a clearer
confirm text, and a separate "Delete last run" action is added for the
run-level operation. Labelling the existing button "Delete run" would have
presented a feed deletion as a run deletion.

FIX: deleteRun guarded on engine.activeRunId(feedId), which returns null for a
run suspended on a manual gate (WAITING_APPROVAL) or on a held step (ON_HOLD),
because both release the engine slot - so a suspended but live run could be
deleted from disk while still present in activeRuns. It now refuses any run
whose status is not terminal (new public WorkflowEngine.isTerminalStatus).

FIX: loadFeeds(force) in overview.html declared its parameter and never used
it, so after a bulk action the grid kept the pre-action status for up to the
10s cache TTL. /api/overview/feeds now accepts an optional refresh=1 that
drops the cache; the default polling path is unchanged.

Verified: node --check on the extracted overview.html inline script; zero
literal escape sequences for newline/CR in JS and zero uncommented Thymeleaf
inlining markers in the template; string/comment-aware brace and paren balance
on both Java files (0/0); activeRunsByFeed and isTerminalStatus extracted
verbatim, compiled with -source 8 and run against synthetic runs (newest-wins
when a feed holds both a parked ON_HOLD and a newer RUNNING run, ON_HOLD and
WAITING_APPROVAL reported, terminal and test runs excluded, startTs ties
broken by runId); the real drillPickRuns / drillIsTerminal / drillUrls /
drillProdChecks extracted from the template and run in node against synthetic
grid rows (CONTINUE selects only ON_HOLD, STOP selects every live status and
picks liveRunId for a run started inside the cache window, an orphaned hold is
reached via lastRunId, Delete last run selects only finished runs with no live
run, skip counts and the PROD checkbox correct).
