filerename: rename a directory's files from a CSV mapping

A new internal executor doing what Rename-FilesFromCsvMap.ps1 does: the
name a file has on disk is built from a template and an id, the name it
must take is read from a column. Same 16 parameters plus -WhatIf, same
defaults, the same checks in the same order, the same log lines and the
same exit codes (0 done, 2 some rows not applied, 1 error or aborted).

Every parameter is a field in the designer, and choosing the executor
writes the script's defaults into the step, so the saved XML states every
value the run uses. A value already present is never overwritten.

The whole mapping is checked before the first rename: a duplicate target
or a name already taken on disk stops the step with nothing renamed,
unless force is set.

The oracle was the script itself, not a reading of it: PowerShell 7.4.6
downloaded for Linux, the script and the executor run on copies of the
same directories.
- 656 executor scenarios (26 targeted, 630 random): final directory,
  exit code, every counter and the ordered REN/SKIP/FAIL/What-if events
  compared. 0 unexplained differences; 25 expected ones asserted in both
  directions (24 of deviation 1 below, 1 host difference: pwsh on Linux
  accepts CR/LF in a file name, Windows and the executor do not).
- The CSV is read by a port of PowerShell's ImportCsvHelper (MIT), not by
  FlatCsvReader: quoted line breaks, skipped blank lines, a BOM overriding
  the charset. 623 CSV texts, 600 of them fuzzed, parsed by Import-Csv and
  by the port: 0 differences.

Deviations, none changing which file gets which name for an input the
script accepted on Windows:
- the {EXT} column is required only when the template uses it; the script
  refused a CSV without it even when the value was thrown away;
- counts are real counts; the script reported list sizes capped at
  MaxReport, so 100 unusable rows read as 30;
- the dry run reports ${wouldRename};
- Stop is honoured between two renames.

Kept as in the script, by choice: a chain in the wrong order (A->B then
B->C) passes the pre-check and fails at run time, leaving the directory
half renamed. Gate 0 Q3 in the spec proposes an opt-in check.

Found on the way:
- JDK 8 Files.move on Windows returns without doing anything for a
  case-only rename (same file); .NET renames. Handled with ATOMIC_MOVE and
  a read-back of the on-disk name.
- The script's default -Encoding windows-1252 is not accepted by
  Import-Csv on Windows PowerShell 5.1 (ValidateSet, 5.1-era source): with
  its defaults it runs only on PowerShell 7.
