ftpsend batch 2: the transport, and a mechanism the spec had wrong

The FTPS client: explicit TLS on the control channel, passive data
connections, binary STOR and SIZE. Six classes added to the ftps package, one
specification correction, nothing else touched. Still no registration and no
pom change, so the package remains unreachable from the running application
until batch 3.

FtpsTransport and FtpsSession are the seam. FtpsTarget is the connection
definition. TrustMode and SslContexts cover the four ways of judging a server
certificate and the PKCS#12 client certificate. JdkFtpsClient is the client.

The specification claimed data-channel session reuse could be had by wrapping
the data socket while naming the control host and port, so that JSSE would
find the control session in its cache. That was measured and it is false. The
client cache follows the socket's real peer port, not the one handed to
createSocket, so naming the control endpoint finds nothing and the client
sends an empty session id. It was isolated in a bench differing from a working
case only in the port actually connected to, and it fails the same way on Java
8 and on Java 21. Section 6 now carries the wrong version struck through.

What works, and what is implemented, is the technique that paragraph
dismissed: the control session is put into the client cache under the data
endpoint's key before the data socket is wrapped, and the handshake resumes
it. Measured to resume on Java 8, which is the production runtime. Where the
internals are encapsulated the injection fails, the transfer proceeds with a
fresh session, and the trace says which of the two happened - a delivery must
not fail over what is, until a server refuses it, an optimisation.

The second prediction in section 14 is now measured rather than predicted. On
Java 8 capped at TLSv1.2 the data channel resumes; with TLSv1.3 available it
negotiates 1.3 and does not, because resumption there is ticket-based. maxTls
is the lever, and that is what it is for.

One defect found by the tests rather than by review: the client handshaked the
data channel when it opened the socket, before sending STOR. A server accepts
the data connection only once it knows what it is for, so both sides waited
for each other. The handshake now happens after the transfer command and its
1xx.

Two behaviours are refusals by design. ASCII mode raises instead of sending
the bytes unchanged, because the files it would carry end their lines with LF
and the protocol requires CRLF: sending them verbatim produces a file that
arrives, reports the right size and is wrong. And a SIZE that the server
cannot answer raises rather than assuming success, because a transfer that
cannot be verified is not a transfer that succeeded.

VERIFIED
- Compiled with javac --release 8 and, separately, with the Java 8 compiler.
- 82 core assertions and 50 transport assertions green on Java 8; 82 and 42 on
  Java 21, the difference being the reuse assertions that only apply where the
  injection is possible. Both runtimes were run because production is Java 8
  and the sandbox default is not.
- The transport tests drive a real FTPS conversation against a server written
  for the purpose: AUTH TLS, the multiline 220 and 230, PBSZ, PROT P, TYPE,
  CWD, PASV, STOR, SIZE, QUIT, over real TLS with certificates generated by
  keytool, including PKCS#12 client-certificate authentication against a
  server that demands it.
- 12 transport mutations, 12 caught, after four came back green and were
  investigated. Two of those four were malformed mutations that never applied.
  The other two were real gaps: the refused-STOR test asserted only that
  something was thrown, which also passed when the client ignored the 550 and
  timed out later on a data connection nobody accepted; and nothing checked
  the final 226 at all. Both tests now assert the reason, and the fake server
  grew a mode where the data crosses and the server then rejects the transfer.
- The UAT failure is reproduced as a test: a server that accepts STOR, creates
  the destination and never accepts the data connection. The client raises,
  and the test asserts the zero-byte shell is left behind - the thing that
  looked like a successful delivery.
- The 227 reply carrying 10.117.145.81 is a test case. The transfer succeeds
  with the substitution on, fails with it off, and the discarded address
  appears in the trace either way.
- The password never reaches the trace; asserted, and the assertion fails when
  the masking is removed.

NOT VERIFIED
- trustMode=WINDOWS. The sandbox is Linux and has no Windows-ROOT store. The
  code reports which provider it needs and the test asserts that message; that
  the store then contains the issuing CA is an inference from the working
  client never prompting, not a measurement.
- Anything against the real servers. Session reuse was measured against a
  server written here, which resumes when asked; whether the real ones require
  it, and whether the passive range is open at all, is still section 2.
- mvn clean package: Maven Central is unreachable from the sandbox.
- ASCII, SITE and dataset names remain deferred with the z/OS target.
