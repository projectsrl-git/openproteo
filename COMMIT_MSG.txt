Copy file list: specification only (batch 0)

Spec at .claude/COPY_FILE_LIST.md for the "copy the files listed in a CSV"
option on filecopy and safecopy. No code: the five Gate 0 questions in
section 9 gate batch 1, and the first of them can change a third of the
work.

ifscopy already has the feature, delivered on 2026-08-21 as 554ed4f. Both
halves of the request are in it: listSource=csv copies exactly the files
named in one column, and the "directory + file name from the CSV"
combination is that shape with listPathPrefix left empty, where the step's
existing IFS source path becomes the base for any name that is not already
a full path. Q1 asks only whether that is the reading, because the other
possible one is a union of the pattern and the list, which no executor has
today and which would be a third shape for all three.

Decisions the spec argues rather than states:

* The reader is EXTRACTED into engine/CopyListSupport (JDK only, no Spring),
  absorbing IfsListSupport, with a two-valued flavour for the one rule that
  genuinely differs between an IFS and a local path. Two implementations of
  one rule that quietly disagree is the failure already met with FileMask
  against elarcheck's matcher. The no-op for ifscopy will be proved
  differentially, pre-patch and post-patch classes compiled side by side and
  compared field by field over a generated corpus, because a reconstructed
  list of the original assertions would only prove the transcription.

* Paths.get(name).isAbsolute() is not a sufficient test on Windows: a
  leading / there means root of the current drive and answers false, so a
  Unix-flavoured list - which is exactly what an earlier ifscopy step
  produces - would be joined under the source directory. The rule is
  isAbsolute() OR a first character of / or \, which also covers UNC.

* The local shape is pre-scanned and ifscopy deliberately is not. Over IFS
  an existence check is a round trip per file and buys nothing the failure
  message does not already say; locally it is a Files.exists on the
  filesystem the copy is about to read anyway. It matters most on safecopy,
  whose whole point is that a process watching the landing zone never sees
  something incomplete - a half-done run leaves correctly renamed files
  there with nothing saying the delivery was short.

* Parameter names and defaults are ifscopy's. PARAM_OPTIONS in
  variables.html is keyed by parameter name with no executor context and
  already carries listSource, hasHeader, onMissingFile and onNameCollision
  with these defaults; reusing a name with a different default is the trap
  recorded for inputCharset between the two ELAR executors.

Read rather than predicted: buildXml emits every <param> generically, so it
needs no change here, unlike reportQuery which was a new child element. But
runFileCopy is dispatched without resolvedParams today - the only copy
executor that is - so the dispatch line in InternalSteps.run() does change.
