ftpsend batch 1: the core, exercised, with one defect found by its own tests

The ftps package: Spring-free, JDK-only, no network, nothing outside it
touched. No registration and no pom change, so no existing feed can behave
differently after this commit - the package is unreachable from the running
application until batch 3 wires it up.

Eleven classes. Glob is the DOS/UNIX mask matcher. FtpReply, FtpReplyReader
and FtpProtocolException are the reply layer. PasvReply parses the 227.
SendMask, FileEntry, PlannedFile, SendPlan and PlanException are the ordered
mask list and the plan it produces. TransferMode is TYPE I and TYPE A.

Glob does not translate the mask into a regular expression. A file mask
carries a dot on essentially every use, and the masks configured in the tool
in service carry '+' and '$' as literals (S211048_TRANSARCH_XF_TAR+$).
Substituting into a regex and missing one escape turns *.tar into something
that also accepts Xtar, which produces a delivery nobody notices is wrong. The
matcher walks the pattern directly, backtracking on the last star, and rejects
a mask containing a path separator rather than letting it silently never
match.

FtpReplyReader honours the multiline form. This is not theoretical: the z/OS
session opens with a two-line 220 and logs in with 230- followed by 230. A
reader that takes the first line and moves on leaves the rest of the banner in
the buffer, reads it as the answer to the next command, and from there reports
every error against the wrong command. Termination is same code then a space,
so an intermediate line that itself begins with digits does not end the reply.

SendPlan builds the whole plan before the first byte moves, which is what
makes a required mask matching nothing fail before anything has been uploaded
rather than halfway through a delivery, and what lets the step log the order
the operator configured so they can check it beforehand. Masks in list order,
files sorted by name within a mask, first match wins, disabled masks not
evaluated.

The sort is explicit and that is the point: directory enumeration is name
order on NTFS and hash order on ext4, so a plan inheriting the filesystem
order would be right on the target and untestable anywhere else. The test
builds the same directory twice, reversed, and requires the same plan.

VERIFIED
- Compiled with javac --release 8, which checks the API surface and not only
  the class file version. No warnings other than the obsolete-source notice.
- 82 assertions, all green, run against the compiled classes. They use the
  real artefacts rather than invented ones: the two 227 replies from the z/OS
  log, the 10.117.145.81 address from the UAT failure, the z/OS 220 and 230
  banners and the BLOCKSIZE multiline 200, and the five real file names of
  40_PACKAGING including the .control at zero bytes.
- 15 mutations, 15 caught. Case sensitivity, '?' arity, star backtracking, the
  path-separator guard, multiline reading, reply termination, the 256 in the
  port arithmetic, the sort, first-match-wins, the required-mask failure, the
  disabled-mask skip, per-mask remote directory, and one-based ordering were
  each broken in turn and each broke at least one assertion.

Two things the tests found rather than confirmed, both recorded because the
point of a positive control is that it sometimes fires.

First, a defect in PasvReply, red on the first run. On rejecting a number over
255 the scan resumed one character in, so a rejected 999 was re-read as an
accepted 99 and the reply parsed into a plausible, wrong port. It now resumes
past the whole number that started the failed attempt.

Second, one mutation came back green: removing the guard that stops a digit
run once it exceeds 255. Investigated rather than filed, and it was a real
gap, not a useless mutation. The outer check catches 999 after the fact, which
is why the suite stayed green, but it cannot catch a run long enough to
overflow the accumulator: 4294967297 wraps to 1 and is accepted as an ordinary
address byte. Two cases were added, the mutation now fails, and the guard is
load-bearing.

One harness weakness was fixed on the way. The disabled-mask mutation aborted
the run with an uncaught exception, so the remaining assertions never ran and
the reported coverage was higher than the real one. Each group now records an
abort as a failure instead of stopping.

NOT VERIFIED
- mvn clean package. Maven Central is unreachable from the sandbox, so the
  build was not run; only this package was compiled, and it references nothing
  outside itself and java.io, java.util.
- Nothing here touches a socket. Everything about TLS, session resumption,
  trustMode=WINDOWS and the network path is batch 2 or later, and the network
  path itself remains what section 2 of the specification says will fail.
- ASCII mode is defined and carried through the plan, but the LF to CRLF
  translation lives in the transport and is deferred with the z/OS target.
