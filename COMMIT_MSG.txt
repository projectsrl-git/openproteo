objpack: discard stale rows on request; look objects up instead of listing

A run on tf0005766 stopped with "line 7: record_business_date 20160921 is
older than 120 months (spec 4)". The feed needs an option to leave such a
row out rather than fail. The same run's console also answered the
question the progress work was built for.

DISCARDING. onStaleBusinessDate = warn | fail | skip replaces the
failOnStaleBusinessDate checkbox. The boolean is still read, and still
means fail, whenever the new setting is absent - so a workflow that ticked
it, as this feed did, fails exactly as before until the choice is changed.
The designer shows such a step as "fail the step".

The window now runs BEFORE object ids are assigned. It used to run in
pre-flight, after ids and file names existed; skipping there would have
left a gap in the OID sequence and a width computed from the pre-discard
count. Kept rows are now numbered 1..N and the OID width follows N.

A discarded row is never silent. In a legal archive it is a document that
does not arrive, so every one - stale under skip, or missing under
onMissingObject=skip - goes to discarded_rows.<base>.csv in the output
directory, with its source line, the reason and every original column. The
name deliberately does NOT start with the submission base name, so a
delivery mask like "<base>.*" can never send it to the archive. Exposed as
${discardedFile}. The missing-object skip used to write one warning per
row; it now shares the file and a single summary line, and warn mode for
stale dates likewise reports one line with a count.

Refused rather than guessed: discarding under a mapped object_id (an id the
feed chose cannot be renumbered, and with rows gone it cannot ascend from
1 - the message says so instead of the sequence error that would otherwise
appear), and discarding every row.

THE MEASUREMENT. The console showed
  listed 19933 files in 101.4s
  read 100 rows, paired 100 objects in 101.4s
All 101 seconds went into listing the objects directory on P: - about 5 ms
per file, two round trips each (isDirectory, then isFile) - to find 100
files. The second line is cumulative; reading and pairing cost nothing.

So in name mode without recursion the directory is no longer listed: each
row's file is looked up directly, one call per row. Only when an exact name
fails to resolve on a CASE-SENSITIVE file system is the directory listed,
once, to match regardless of case as a listing always did. With recursion
the listing stays. Case sensitivity is ASKED OF THE FILE SYSTEM, not assumed
from the platform: the objects directory's own name with its case flipped
must resolve to the same canonical path, so sibling folders that differ
only in case do not fool it; if the probe cannot tell it answers
"sensitive", and being wrong costs a listing - the old behaviour, slow but
never incorrect. Names that are not plain file names (sub/x.json, ../m.csv)
are never resolved as paths in name mode; a listing never matched them.
