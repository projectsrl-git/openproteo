Log report Batch 2b: the /logs page, one grid with a source selector

One page and one grid, with a source switch rather than two tabs: Events reads /api/logs/search and
Runs & output data reads /api/logs/runs. The filter bar, the paging and the grid are shared; only the
columns and the two source-specific filters change, so switching source keeps the current selection.

The filter bar is built from /api/logs/facets: source id, target id, feed with its name, event,
severity and run status, plus free text, a from/to range and the user. Event and severity are shown
for events, run status for runs, and everything else applies to both.

Events show when, feed with its PROD flag and name, source, target, run, step, event, a severity badge,
user and details. Runs show started and ended, feed, source, target, run, a status badge with the run
message, the trigger and who started it, the steps ok out of total with failures highlighted, and the
output data rendered as description equals value -- the same information Operations displays. The feed
links to the workflow page and the run id to the existing run page, so the grid is a jumping point into
the app rather than a dead end.

Paging is server side, a hundred rows per page, with prev and next and an x-y of N counter. The footer
also reports what the index currently holds -- events, runs, outputs and the window in days -- so an
empty result is easy to tell apart from an empty index.

The route was added to PageController with a link on the dashboard, and the page uses the new
cache-busting includes.
