designer: redraw the elarxml panel when the content source changes

Reported from the designer with a screenshot that showed the contradiction
plainly: IFS selected in the dropdown, and underneath it the LOCAL
explanation, no IFS base path, no listing cap and no datasource selector. The
step could not be configured for IFS through the interface at all.

The panel shows a different set of fields for LOCAL and for IFS, so changing
the source has to redraw it. The pattern for exactly this is already in the
file - diffSetMode and ifsSetListSource both set the parameter and then call
renderNodes - and the batch 3 select called setNodeParam alone. The value was
stored correctly; only the page contradicted itself. Now elarSetContentSource.

THE TEST HID IT, WHICH IS THE MORE USEFUL HALF

The jsdom suite set the parameter and then called renderNodes itself, which is
doing by hand the step the page never did. Every assertion about the IFS
fields then passed, because the harness performed the redraw. A test that
supplies the missing step cannot fail on it.

The suite now finds the select in the rendered panel, asserts that its handler
is not a bare setNodeParam, and executes the onchange attribute as a browser
would. jsdom does not run inline handlers, so dispatching a change event does
nothing and the attribute has to be evaluated directly. It then asserts the
panel really changed: the LOCAL explanation is gone.

The rule this leaves: drive a control through the handler the page wires to
it, never around it. Any step the harness performs on the page's behalf is a
step the page is no longer being tested for. The other conditional panels are
worth checking the same way.
