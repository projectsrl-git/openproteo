objpack: compression, and the name the specification will not choose

Gate 0 9.4 answered: follow the specification and allow compression where
it permits it. gzip is implemented; bzip2 and xz are refused with the
reason.

THE DECISION THE SPECIFICATION DOES NOT MAKE. Section 2 requires every
file of a submission to share one base name and all its examples end
.tar. Section 3.5 permits gzip, bzip2 and xz for the archive. Those cannot
both hold literally, because a gzipped archive is .tar.gz - so the code
has to choose a name, and the choice belongs in the open. The reading
taken: the "Do not" box forbids compressing the CONTENTS of the package,
members ending .zip or .7z, while "Do only use" permits compressing the
whole archive with one of the three named algorithms, in which case the
extension has to say so. Naming a gzipped file .tar would misdeclare its
type to the receiver, which is worse than extending the name. The .md5
keeps its own name and holds the hash of whatever is delivered. This is
written into SubmissionName.archive, the guide and the panel, so if the
archive team reads it differently there is one sentence to change rather
than an assumption to hunt for. STILL UNCONFIRMED BY THE ARCHIVE TEAM:
that they accept .tar.gz at all.

THE PLATFORM LIMIT, MEASURED NOT ASSUMED. GZIPOutputStream is in the JDK.
BZip2OutputStream is not, org.tukaani.xz is not, commons-compress is not
on the classpath and not in pom.xml - all four checked by loading the
classes. bzip2 and xz would each mean a new dependency that cannot be
confirmed against the internal Nexus from here, so they are refused with
that reason rather than silently downgraded to gzip or accepted and
ignored.

HOW IT IS BUILT. The compressor wraps the tar stream as it is produced, so
no uncompressed intermediate is ever written - the same reasoning that
keeps the objects from being staged. The finished package is then read
back THROUGH THE DECOMPRESSOR, so what is verified is the file that will
actually be delivered. UstarReader gained a sequential stream reader with
a skipFully that does not trust InputStream.skip to move everything it is
asked to.

An ftpsend mask of *.tar stops matching a compressed package. That is a
real operational trap, so it is called out in three places: the panel
warns the moment gzip is selected, the guide states it as the first
consequence, and the mask failing to match fails that step - the good
outcome, since it stops rather than delivering half a package.

VERIFIED: 113 assertions green (103 in PackSuite, 10 cross-reader on the
compressed package: file identifies it as gzip, gunzip -t validates the
stream, GNU tar lists the same six members in the same order and extracts
them byte-identical, the .md5 matches md5sum of the .tar.gz, the
compressed file is smaller, and no uncompressed .tar is left behind). 26
mutations, ALL CAUGHT. Three did not pass first time and NONE was a code
defect: one mutation did not compile, being malformed in the runner, and
was repaired rather than counted; THE MD5 GAP WAS REAL - hashing the wrong
file survived because the suite only checked the .md5 against what the
step reported, which is self-consistent whatever was hashed, while the
bash cross-check that did test it is not run by mutations, so the suite
now hashes the delivered archive independently; and the first skipFully
mutation was EQUIVALENT - moving "left -= got" out of the branch changes
nothing because got is zero on the path that falls through - replaced with
one that claims the whole skip succeeded, now caught by a test that reads
the package through a stream whose skip() refuses to move more than one
byte, since GZIPInputStream otherwise never exercises that loop.

One suite assertion failed on the first run and it was an expectation that
had aged: it asserted gzip was refused with "not implemented", true until
this batch. The code was right; the test recorded the old behaviour.
