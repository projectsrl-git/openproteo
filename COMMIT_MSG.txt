ifscopy: copy the files listed in a CSV column

A new param, listSource, gives the IFS copy executor a second shape. Absent or
'pattern' is exactly today's behaviour, including the variables it publishes;
'csv' copies exactly the files named in one column of a CSV, typically the
output of an earlier step. An unrecognised value FAILS rather than falling
back
to 'pattern', because a typo would otherwise be answered by a directory copy
with no pattern set - that is, everything.

Params (new shape only): listFile, listColumn (header name, matched
case-insensitively, or a 1-based index tried only when no column carries that
name), listPathPrefix, listDelimiter (empty = detected, via the same
detectDelimiter csvsql uses), listCharset, hasHeader, onMissingFile,
onNameCollision. Nothing was added to StepDef, the parser, the writer, the DTO
or buildXml: params round-trip already.

The prefix falls back to the step's existing IFS source path field, so a list
of bare names needs no second copy of the directory it came from; a name
starting with / is a full IFS path and the prefix is not applied. Which base
was used is stated in the log. A backslash in a name is left alone: it is
legal
in an IFS name.

Missing file and local-name collision both fail by default. A collision
(/one/x.pdf and /two/x.pdf both landing on x.pdf) is caught before anything is
copied, because otherwise the step reports success with fewer files than it
copied. The same path twice is a duplicate - collapsed and counted - not a
collision. Rows read, duplicates, and rows with no file name are logged before
the transfer starts, with the first fifty line numbers named and the counts
uncapped.

No existence pre-scan, unlike elarxml: the destination is a step working
directory, not a delivered set, and a pre-scan would cost the whole transfer
twice over. copyListToLocal returns rather than throws, so the counters are
still published when it stops.

New outputs in this shape: listRows, listedFiles, duplicatesInList,
blankNames,
missingFiles, skippedExisting.
