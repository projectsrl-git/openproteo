elarxml: delete the staged copy when its INDX is delivered

New step parameter deleteContentAfterEmbed, OFF by default: each embedded
document is removed from the family's documentPath once the INDX carrying it
has reached its final deliverable name. Those documents are copies staged by
an ifscopy step and the archive still holds the originals; the first real run
of CLIAC@DT left 9.3 GB of them behind after the feed had gone out.

The moment is the design. writeDocument writes into a batch under the
in-flight I_PART/P_PART names and the final name only arrives in
Batch.close, so deletion is anchored to closeBatch - the same event that
already anchors the .done rename and the .skipped commit. Three paths
discard an open batch in
between: an exception aborts it, the disk guard cuts the input into
.remaining.csv, and an oversize document rolls it. Deleting at write time
would look identical on a good run and leave .remaining.csv referencing files
that no longer exist, which the default onMissingFile=SKIP would then drop
without failing the run.

DeletableContentStore is a new interface implemented only by
LocalContentStore. IfsContentStore is outside that package and does not
implement it, so deleting over IFS is unreachable because there is no method
to call, not because a check forbids it. contentSource=IFS with the flag set
is REFUSED (exitCode 2), not warned about as contentIfsPath under LOCAL is: an
inert setting still gives the operator the run they asked for, while silence
here would withhold the one thing they turned it on for. clientValidate
refuses the same combination at save.

A delete that fails is counted in documentsDeleteFailed, named in the log and
never fatal - the INDX is already delivered. One line per batch, ten names at
most. summary() mentions deletion only when the option is on. An INDX that
commits while its PULL cannot be published deletes nothing, including
documents already inside the delivered INDX.

VERIFIED
- Standalone suite compiled and run with javac --release 8 against the real
  ElarRun: 32 assertions, 0 failures. The INDX is byte-identical (SHA-256)
  with and without the option. A batch whose PULL cannot be published keeps
  every document. Every row in .remaining.csv still has its file.
- The suite bites: deleting after writeDocument fails 2 assertions, deleting
  in the finally fails 1. Two earlier scenarios of mine were blind and were
  replaced; the note records why.
- Designer under jsdom: 11 assertions, 0 failures. The checkbox is driven by
  compiling its own onchange attribute and calling it with this bound to the
  element. Elements counted inside the card, not innerHTML matched as a
  string. Two mutations fail it.
- Scans: no Thymeleaf inlining tokens outside comments, no literal escape
  sequences in inline JS, node --check on both inline scripts, brace balance
  ignoring strings and comments on all four Java files.
- tools/scan_panel_redraw.js: 120 parameters (from 118), 0 defects.
- USAGE.md rendered by the real render() extracted from docs.html: 78
  headings, 349 paragraphs, 5 code blocks, no raw Markdown outside code
  blocks.

NOT VERIFIED
- mvn clean package. The internal Nexus is unreachable from the chat sandbox;
  the build on the target machine is the only proof.
- The Windows failure mode. A file held open by a scanner or the indexer is
  exercised by a test double that refuses on purpose, not by a real lock: what
  is shown is that a refusal is counted and does not fail the run, not that
  the delete succeeds under a scanner.
- Nothing touching IFS. Jt400Ifs has still never been executed.
