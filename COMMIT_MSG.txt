elarxml batch 3: streaming Base64 and SHA-256, skip accounting

The content embedding, and the last of the three accumulations that caused the
OutOfMemoryError.

ContentEmbedder performs the two passes the template forces: the hash element
precedes the content element, so the digest has to be known before the payload
is written. That is the same number of reads the legacy tool already
performed, since it read the file once for readFileBytes and again for
FileHashSHA256. What changes is that neither pass holds the file. The digest
streams through MessageDigest in blocks, and the Base64 streams straight to
the writer in chunks that are a whole number of three-byte groups, so every
full chunk yields complete quads with no padding and no state carried between
chunks - padding appears exactly once, on the final partial group, which is
where Base64 puts it.

The digest is over the raw file bytes. That is the only convention ever
executed: IndxBuilder.computeSHA256 over the Base64 text exists but is never
called, and every INDX ELAR has accepted carries the raw-bytes digest. The
test asserts not only that our digest matches a one-shot digest of the same
bytes but that it differs from the digest of the Base64 text, so the two
conventions cannot be confused later.

fill() loops on the count returned by read. That is the defect the prototype
encoder in the legacy estate had: it allocated a buffer the size of the whole
file, called read once, and discarded the returned count, so any short read
left the tail as zeros and Base64-encoded them with no error. Looping is the
fix, and it also guarantees every full buffer is a whole number of three-byte
groups.

The guard for a content file changing between the two passes fails the batch
rather than the document, as decided in section 4.1 of the spec. Size and
modification time are captured before the digest, and the encoded byte count
is compared against them during the encode pass so the failure is immediate
rather than at the end. By that point the hash and most of the payload are
already in the output stream and cannot be retracted, so the only outcome
consistent with temp-then-rename is to discard the whole batch, and the
message says so. Both directions are tested: a file that grew and a file that
shrank.

encodedLength gives the Base64 length a file of a given size will produce,
which is what batch 4's byte budget will compare against the remaining space.
It is verified exact against the real encoder at nine sizes rather than
assumed approximate, because a budget built on an estimate that drifts would
roll over in the wrong place.

ElarCounters counts skipped documents by category and reports them. The legacy
tool printed "Skipping doc: file not found" to stdout with no counter and no
aggregate, so a batch that had silently dropped half its documents looked
exactly like a successful one and the only way to find out was to count blocks
in the delivered XML by hand. The summary states the skip counts even when
they are zero, because a line that only appears when something went wrong
trains people not to look for it.

Verified with 28 assertions compiled with --release 8 and run: the digest
against a one-shot digest and against the Base64-text convention, the known
SHA-256 of an empty file, the streamed payload identical to a one-shot encode,
all twelve size classes across the chunk boundary and both padding cases, the
wrapper still holding on a 70 KB file at a 100-character limit with nothing
over the limit and every payload line a whole number of quads and the payload
byte-identical once the breaks are stripped, both change-between-passes
directions, the size estimate at nine sizes, and the counters including that
the summary is counters only and can leak no record. The batch 1 and batch 2
suites were re-run and pass.

ByteArrayOutputStream now appears zero times in the package. The buffer that
held each whole file before encoding is gone by construction rather than by
discipline, and the scan for it joins the ones for StringWriter and
Transformer.

NOT verified: mvn clean package, and any of this against a real content file
on G:. The digest is the piece to check first, since it can be compared
against a delivered INDX: take any document from one, and the HashValue should
match the SHA-256 of the source file's raw bytes.
