Variables page: show steps only SOME selected feeds have

Implements the read-only half of section 3 of
.claude/SQLREPORT_VERSIONING_VARIABLES.md and answers its two open questions.
[Add to all selected] is batch 2 and is deliberately not in here.

The multi-feed editor showed only the INTERSECTION of step ids, which silently
hid every difference: a step you cannot see is a difference you cannot act on.
A new "Steps missing from some feeds" section now lists every id present in
some but not all of the selection, each with an "in N of M feeds" badge, its
executor, the feeds it is missing from (truncated at six, full list in the
title on hover) and a read-only preview of the fields and params common to the
feeds that do have it.

Open question one, answered: when the same step id uses a DIFFERENT executor
depending on the feed it is flagged as a conflict naming both executors,
rather than hidden. The reason is not tidiness - "query" on a sql step and
"query" on a csvsql step are different things, so a mass edit would write a
value that is wrong in half the feeds. Batch 2 must refuse to add those.

Open question two, agreed and deferred to batch 2 where the action will exist:
adding a step to a PRODUCTION feed will require the same explicit confirmation
as Clear History, opConfirm with danger and a required checkbox naming how
many PROD feeds are included.

The section is deliberately read-only. Rendering editable inputs here was
rejected: an edit made in a section titled "missing from some feeds" would
apply to a subset and the operator would have no way to tell from the result.
The preview inputs are disabled AND carry no data-scope, which is the actual
safety mechanism - saveVariables() collects .vval[data-dirty="1"] and
dispatches on data-scope, so an input with neither can never enter the
payload.

Why the split: making the difference visible is pure UI, touches one template
and cannot damage anything, while creating a step in the feeds that lack it is
a structural write to N workflow XML files, needs an explicit insertion
position, and interacts with the versioning trigger of section 2 - adding a
step to a feed that already ran is exactly what section 2 wants to intercept.
Shipping them together would have put a zero-risk improvement behind a change
that deserves its own review.

Verified. The real renderCommon was extracted from the template and run
against a fake DOM with five synthetic feeds: a common step, a step missing
from one feed, one missing from three, one present in a single feed, and an id
whose executor differs. Asserted, all passing: the common section still counts
only the truly common id, the partial section counts three, every badge reads
the right N of M, the executor conflict is detected and names both executors,
the missing-feed lists are correct, the hover title carries the full list, and
the invariant that matters - every disabled input has no data-scope while
every enabled one has one, and no disabled input is dirty. node --check on the
page's inline JS passes, there are zero literal newline/CR escape sequences
(the hover title builds its line breaks with String.fromCharCode(10)) and no
Thymeleaf inlining markers. Every CSS variable used by the page style block
was checked against app.css: --bg-raise, --ink-faint, --fail and the rest are
all defined, none invented.

NOT verified: mvn clean package (no Java changed in this patch, but the build
is still the only final proof) and the page as rendered by a real browser.
