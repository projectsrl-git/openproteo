Show the build version (pom version + git commit) in the topbar

See at a glance which build is running. Nexus-safe, with no new Maven plugin: Maven filters a tiny
properties file with the pom version and a commit hash passed on the command line, an endpoint reads it,
and the topbar shows a small badge.

- src/main/resources/build-info.properties carries three placeholders (build.version=@project.version@,
  build.commit=${git.commit}, build.time=${maven.build.timestamp}); @...@ is used for the version so it
  does not clash with the ${...} build properties.
- pom.xml filters ONLY that file via an explicit <resources> block (one filtered resource limited to
  build-info.properties, one unfiltered for everything else, so no binary or static asset is touched). The
  git.commit=unknown default and the build-timestamp format are added to the EXISTING <properties> block.
- ApiController.buildInfo() loads the file once (cached), blanks any raw placeholder left by a plain
  build, and exposes version / commit / shortCommit / buildTime. New endpoint GET /api/version; the same
  map is folded into /api/env.
- theme.js mountVersion() fetches it and adds a small .ver-badge to the topbar next to the clock
  ("v1.0.0 · <short>", full details in the tooltip); app.css styles it with a light-theme override.

The deploy .bat builds once to verify, commits and pushes, then rebuilds the WAR passing
-Dgit.commit=<short HEAD> so build-info.properties inside the WAR carries the real hash. A plain
`mvn package` still shows the version, with the commit left blank.

Docs: .claude/2026-07-25-build-version-badge.md and CLAUDE.md.

Verify: buildInfo() was compiled and executed against a sample build-info.properties and returns the map
with a 7-char short commit; theme.js passes node --check with no literal \n/\r; pom.xml is valid XML with a
single <properties> block. Java not compiled as a whole in the chat sandbox -- run the Maven build on deploy.
