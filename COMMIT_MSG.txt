Keyed variable lookup ${COL@key}

Prerequisite for the sqlreport executor, and the decision recorded in its spec: values collected from a
query are addressed by key rather than by position.

VarResolver now resolves ${COL@key} by finding key in the companion list ${COL.keys} and returning the
value at the same position in ${COL}. Both lists are semicolon separated and aligned, which is how a
result set indexed by a key column is published, so a step can write the amounts and the client ids
together and a later step can ask for ${AMOUNT@CID12345} without knowing which row that client is on.
Positional indexing keeps working exactly as before and OUTPUT DATA still renders the lists unchanged.

Two deliberate choices in the lookup: a key that is not present resolves to an empty string, and so do
two lists of different lengths, which is the signal that the variables were not produced together.
Returning a neighbouring row would be far worse than returning nothing in a reconciliation. Keys are
compared trimmed and case-sensitively.

Docs: USAGE.md, the spec in .claude/SQLREPORT_VERSIONING_VARIABLES.md and CLAUDE.md.

Verify: the real resolver was compiled and executed - lookups by key on two different collected columns,
a key in the middle and at both ends, an absent key, deliberately misaligned lists, positional indexing
still working alongside, the bare list variable untouched, an unknown base variable, and two keyed
references inside one string.
