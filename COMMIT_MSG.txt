elarcheck: the designer configuration panel

Closes the gap the executor's own commit message and spec both recorded.
elarcheck was in the executor dropdown of designer.html but had no branch of
its own, so a step fell through to the generic external one: name/value param
rows, an output-var repeater it has no use for, and a Script field reading
"not used for this executor". Every parameter had to be typed by hand as a
name/value pair with nothing to say what the names are, and this executor has
fourteen of them, thirteen optional. Built on the elarxml panel from the
previous commit, which is now the model for both.

The panel is inputDir, the only required parameter, then three collapsible
subsections grouped by what is decided together rather than listed in
declaration order. Line length puts the target beside the receiver limit with
the reason they are two findings and not one written between them. Element
names carries the three local names plus the mandatory list, together with the
note that a tag missing on nearly every record is a mapping problem while one
missing on three records is a data problem: that sentence tells an operator
which of the two they are looking at, and it belonged beside the field rather
than only in USAGE.md. Optional checks and reporting holds the
already-delivered directory, the findings cap and the three switches.

Each field carries the executor's own default as its placeholder and its
reasoning in a title, so the why travels with the field. Three reasons that
are easy to lose now sit on the screen beside their setting: the charset is
deliberately NOT the one the files declare, because trusting the declaration
would surface an encoding mismatch as a spurious structural error; the
findings cap caps the LIST and never the counters; and failOnFindings is off
so a gate can branch on the counters, since a step that always failed could
not drive the check-then-repair shape this executor exists for.

Two properties are stated in the panel rather than left to the documentation:
that the executor is read-only by construction, which is what makes it safe
against a live delivery folder, and that no field value reaches the findings
file or any log line. The first is why it can be pointed anywhere, the second
is why it can be pointed at files carrying customer names and tax codes. Both
are asserted by the test, so they cannot quietly fall out of the panel later.

clientValidate requires inputDir and refuses a target line length above the
receiver limit. The executor accepts that combination and the two findings
then read backwards, with "over target" becoming the rejection and "over the
receiver limit" the survivable one, which is worse than a refusal. Equal
values are allowed: the receiver limit is a bound, not a strict outer one.

inputCharset was deliberately LEFT OUT of the Variables page's PARAM_OPTIONS.
That table is keyed by parameter name with no executor context, and the two
ELAR executors share the name with different defaults, UTF-8 for elarxml and
windows-1252 for elarcheck, so one dropdown would print the wrong default for
one of them. On a mass-edit page a confidently wrong label is worse than a
free-text box. The unambiguous enums were added: checkPull, verifyHash,
failOnFindings.

buildXml needed no change. Every field is a step param, which it already emits
generically.
