objpack: the designer panel

Batch 3. Four sections - Submission, Source metadata and objects, Column
mapping, Package and checks - plus objpackBase, which previews the
submission base name live under the four fields that produce it.

WHY THE PREVIEW. Every artifact of a submission shares one base name, and
spec section 2 makes it the thing that must be unique and must not change
when a submission is retried. A wrong feed id or a mistyped date is
therefore not a small error: it is a submission that collides with an
earlier one or is rejected on arrival. The preview shows
tf0002448.20260918.S001.V001 as the fields are typed and says what is wrong
when something is. It mirrors SubmissionName exactly - three-digit padding,
lowercased feed id - and a ${variable} in the date is passed through and
NOT flagged, because it resolves at run time and the panel has no business
calling it malformed.

WHAT THE PANEL DELIBERATELY OMITS. compression is not offered: while Gate 0
9.4 is open its only valid value is none and the executor refuses anything
else, and a control whose only correct setting is the default is a way to
get it wrong - the same reason oidPadding was dropped as a parameter in
batch 2. orderBy appears only when pairing is by row order, because it
means nothing otherwise. onMissingObject, failOnOversize and
failOnStaleBusinessDate are present precisely because those are Gate 0
questions still open: the conservative default is preselected and the
alternative is one click away instead of being a parameter nobody knows
exists.

VERIFIED. The panel's parameter names were compared MECHANICALLY against
what the executor reads: every setNodeParam key from the panel branch
against every pv(params, vars, ...) key from runObjPack. 32 written, 33
read, nothing written that is never read, nothing validated that cannot be
set. The single read-but-absent key is compression, the deliberate omission
above. This check exists because a panel writing map.objectID while the
executor reads map.objectId is silently broken and no compiler would ever
say so. Also: node --check on the extracted inline JavaScript with a
positive control proving it can fail; 11 assertions on objpackBase run
under node covering lowercasing, padding, the empty step showing
placeholders rather than a wrong name, a short feed id, a dashed date, a
${variable} left alone and a zero sequence clamped; markup tag balance
inside the panel (55 div, 5 select, 33 label, each matched).

6 MUTATIONS OF THE PREVIEW LOGIC, ALL CAUGHT - after the harness was fixed.
One "survivor" in the first run was nothing of the sort: the sed anchor did
not match, so the unmutated test ran and passed. The harness now compares
the file before and after and reports ANCHOR MISSED rather than counting it
green. That is the same failure as a check reading the wrong exit status,
which happened earlier in this same session: a test that cannot fail is
worse than no test.

The brace-balance tool reports identical counts on designer.html before and
after this change, so its non-zero figure is the surrounding HTML being
counted as code rather than a defect introduced here. For this file node
--check is the authority.

not re-run. USAGE.md is batch 4.
