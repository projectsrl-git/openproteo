Publish the datasource a step ran against as a step output

Every executor that takes a datasource - sql, sqlreport and ifscopy - now
publishes it, so it is recoverable afterwards as ${<stepId>.dataSource}
through the engine's existing namespacing, and unqualified as ${dataSource}
like any other step output. No new mechanism and no new variable machinery:
the value simply goes into res.outVars and the engine does the rest.

It is published as the FIRST statement of the executor, before the datasource
is even looked up in the registry. That is deliberate: "which database did
this actually hit" is a question that matters most precisely when something
went wrong, and the engine merges outVars after every attempt regardless of
exit code, so the value is there for a step that then fails - including one
that failed because the datasource id was wrong, where seeing the id that was
tried is the whole answer. It is also what lets the audit report state which
database a run hit rather than only which step ran.

Two names are published for one value, dataSource and datasource. The XML
attribute is spelled all lowercase while every other step output in this
codebase is camelCase, so whichever of the two an author types would otherwise
resolve to an empty string in silence - the exact failure mode that cost a
debugging session recently on a step id typo. The alias is one line; the wrong
guess is a session. Both names are also in sqlreport's STEP_OUTPUT_VARS so
their value is echoed normally in the step log instead of being treated as
collected, possibly personal, query data.

Verified end to end rather than by inspection: the REAL VarResolver was
compiled together with a transcription of publishDataSource and of the
engine's namespacing loop, and 10 assertions all pass. The requested
${SQL_EXTRACTION.dataSource} resolves, so does the lowercase alias, so does
the unqualified ${dataSource}, and so does the form embedded in a larger
string. With two SQL steps in one run each keeps its own qualified value while
the unqualified name is the last writer, as for any step output. A step with
no datasource publishes nothing at all, an unknown step id resolves to the
empty string and never to a neighbour's value, and surrounding whitespace is
trimmed. Brace and paren balance is 0/0 on InternalSteps.

NOT verified: mvn clean package, and a real run. The quickest check on deploy
is to put ${SQL_EXTRACTION.dataSource} in a setvar or in OUTPUT DATA and
confirm it shows the datasource id.
