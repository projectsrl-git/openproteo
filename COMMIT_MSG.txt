XML tree view, and a standalone xml_viewer.html

Item 6 of the list. The XML viewer had only a formatted code view; reading a
workflow definition that way answers "what does the file say" but not "where
is this element and what is under it", which is the question actually being
asked.

An .xml file now opens with two tabs. Code is the formatted source as before.
Tree renders the same document as collapsible rows: click an element to open
or close it, Expand all and Collapse all, and a single search box that matches
tag names, attribute names, attribute VALUES and text content at once. Matches
are highlighted with mark, branches with no match are hidden, and the
ancestors of every match are opened so a hit is never buried inside a closed
node. Element headers and text content have different backgrounds and
attribute names and values are coloured apart. The tree is built lazily on the
first click of the tab, so opening an XML file costs nothing extra, and a file
that is not well-formed says so and stays readable under Code.

Every colour is an existing app.css variable rather than a literal, which is
what makes the light theme work as well as the dark one; each variable was
checked to resolve in the light block too, and none was invented.

The same viewer also exists as a standalone page, xml_viewer.html in the
repository root, alongside csv-viewer.html. Browse or drag-drop a file, same
tree, same search, its own theme toggle, and zero external references -
asserted, not assumed - so it works on a machine with no access to OpenProteo
and the file never leaves it. The renderer is written once and injected into
both files so the two cannot drift apart.

Verified. jsdom was installed in the sandbox so the real renderer could be run
against a real DOM, and 30 assertions pass against a realistic workflow XML:
escaping and highlighting including a query that is itself an XML
metacharacter, the node count, the root tag, attributes rendered as name and
value pairs, text in its own row and trimmed, entities decoded by the parser
and then re-escaped safely, comments shown rather than dropped, child counts,
indentation growing with depth, collapse all leaving the root open, expand all
reopening, search matching an attribute value, a tag name and text content,
case-insensitivity, a term matching several nodes, a term matching none hiding
everything, clearing the search restoring everything and removing the
highlights, and a malformed document being detectable.

That run caught a real bug before delivery: the row labels are written by
paint(), which was only ever called from search(), so the tree rendered
completely BLANK until the user typed something. It is fixed with an initial
paint(''), and the assertions that failed on it now pass. Without a real DOM
this would have shipped. node --check passes on viewer.js and on the
standalone page, both with zero literal newline/CR escape sequences.
