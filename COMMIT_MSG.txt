ftpsend fix: the masks never reached the file, and the checklist was wrong

Reported: two send patterns added in the designer, saved, gone. The masks were
being written into the preview pane and dropped by everything downstream of
it.

The designer's buildXml is the preview and the download, and it never reaches
the disk. Saving posts the workflow as JSON, which becomes a WorkflowDto and
is re-serialised by WorkflowXmlWriter. The DTO had no sends field, so Jackson
discarded the array without a word; the writer emitted no <send>; the parser
read none back. Three places, all missed, in both directions - a workflow
saved this way also reopened without its masks, because the StepDef to DTO
mapping had the same hole.

The batch 3 checklist covered the six places an executor KIND has to be
registered. A repeated child element has its own set, and only one of them
overlaps. Reading the parser and the panel and inferring that the designer's
XML was what got saved is exactly the substitution of a plausible deduction
for a read that the contract warns about, and it produced a feature that
passed 42 panel assertions and lost the data anyway.

Three places fixed: SendDto and the sends list on NodeDto, the <send> block in
WorkflowXmlWriter, and the StepDef to DTO mapping in ApiController so a saved
workflow reopens with its masks in order.

VERIFIED
- A round-trip test over the path a save actually takes: DTO, writer, XML
  file, parser, StepDef. Both the writer and the parser are JDK-only, so this
  runs against the real classes and not against stubs. 22 assertions.
- The reported bug is reproduced by it: suppressing the writer block takes the
  suite from 22 green to 7 failures, the first being that no <send> is
  emitted.
- Order is checked against a NON-alphabetical sequence, so a writer that
  sorted would be caught - a mutation that sorts fails on exactly that
  assertion. With the two masks of the report, *.md5 and *.tar, sorted and
  given are the same string and the test would have proved nothing.
- 6 mutations, 6 caught: the block removed, the list sorted, transfer written
  when it is BINARY, an empty row written as an empty mask, and each of
  optional and enabled dropped on the way out.
- Saving twice is exercised: parse, map back, write again, and assert the
  order and every flag survive. Losing them on the second save is the same
  shape of bug as this one.
- Patch applied on a second clean clone at f69f350, compared byte for byte,
  and the round trip re-run from the applied tree.

One harness weakness fixed on the way, for the third time in this feature and
this time it had crept back in: the reproduction of the bug printed nothing at
all, because the suite threw on an index past the end of an empty list and
died before the summary. An aborted phase now reports the count it reached, so
a mutation that crashes is comparable with one that fails an assertion rather
than being read as green.
