Copy file list: the filecopy and safecopy executors (batch 2)

engine/LocalCopySupport, JDK only, is the transfer half of the option whose
reading half batch 1 extracted. InternalSteps.runCopyList is the one body
both executors share - they differ only in whether each file is staged
under a temporary name first. Both gain the listSource switch, filecopy
finally receives resolvedParams (it was the only copy executor that did
not), and ifscopy is untouched: CopyListSupport is byte-unchanged by this
batch, asserted rather than assumed.

Engine only. The option is NOT reachable from the designer yet - no panel,
and clientValidate still requires source unconditionally. That is batch 3.

Decisions worth the words:

* The pre-scan is why the local shape differs from ifscopy. Over IFS an
  existence check is a round trip per file and buys nothing the failure
  message does not already say; here it is a Files.isRegularFile on the
  filesystem the copy is about to read anyway, so the step refuses BEFORE
  copying anything instead of stopping half way. It matters most on
  safecopy, whose whole purpose is that a process watching the landing zone
  never sees something incomplete - a half-done run leaves real, correctly
  renamed files there with nothing saying the delivery was short.

* A listed name already ending in the temp suffix is REFUSED, not skipped.
  Under a pattern, skipping is right: it is somebody else's in-flight file
  and nobody asked for it. In a list it was asked for BY NAME, and
  delivering it would put a file into the landing zone under a name every
  watcher is built to ignore - a delivery that silently never arrives.

* A bare name with no base at all is refused, where ifscopy only logs.
  There a bare name still lands in the connection's home directory; here it
  would resolve against Tomcat's working directory. The message names both
  fields that fix it.

* mode=move and mode=list are refused with a list (Gate 0), naming the mode
  rather than silently downgrading to a copy or ignoring the setting.

Verified:

* THE EXECUTORS ARE RUN, NOT REVIEWED. runFileCopy, runSafeCopy,
  runCopyList and their four helpers are lifted VERBATIM out of
  InternalSteps.java at build time and compiled against the real StepDef,
  VarResolver and StepExecutor.Result - all Spring-free - then exercised
  against real files on disk. 141 assertions, 14 mutations of the real
  sources, all caught.

* The pattern shape is proved unchanged the way batch 1 proved the reader:
  pre-patch and post-patch bodies over identical trees across eight
  pattern/mode scenarios, comparing exit code, every published variable,
  the destination listing, the source listing afterwards and the whole log.

* That safecopy stages under the temp name cannot be deduced from the
  result, so the destination is WATCHED WHILE THE COPY RUNS and the
  in-flight name has to be seen. The mutation that writes straight to the
  final name is caught by that assertion and by nothing else.

Three things the run found and review would not have:

* A mutation reported as caught and was not: the collision-guard anchor
  occurs TWICE in InternalSteps, runIfsCopyList carrying the identical
  line, so the edit landed on ifscopy, which this suite does not exercise.
  It still read as caught because the suite was flaking at that moment -
  two independent faults agreeing to produce a pass.

* The suite was flaky, 2 runs in 10: the in-flight watcher also asserted it
  had seen the FINAL name, which races its own shutdown and is redundant
  with the final listing. Removed, then 15 consecutive clean runs before
  any mutation result was trusted.

* An assertion of mine was wrong rather than the code: FileTime.equals
  compares nanoseconds and this filesystem truncates them, so "attributes
  preserve the modification time" failed while working. It now stamps the
  source in 2020 and asserts filecopy keeps that time and safecopy does
  not - the actual difference between the two, never asserted before.

Known duplication, deliberately not removed: runCopyList repeats much of
runIfsCopyList's parameter reading and reporting. Merging them would change
ifscopy's log wording, which no feed asked for; the part where a divergence
would cost something, the reader, is already shared.

Not verified: mvn clean package, and InternalSteps.java as a whole. Not run
on Windows - the separator and drive-letter rules are batch 1's, whose
Windows half remains an argument from the documented semantics of Paths.
Not exercised on a list of tens of thousands of files: the list is held
whole, as ifscopy holds it, and one log line per file still stands.
