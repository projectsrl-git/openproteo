elarxml: designer panel, and rename each input to .done per file

Two defects reported from the first real use of the executor.

1. The .done rename ran once at the end of the run. ElarRun renamed the
processed inputs after the last batch of the last file, so it renamed either
all of them or none. A run of three CSVs whose third failed left the first two
DELIVERED BUT NOT RENAMED, and the next run reprocessed them: colliding
filenames when output.start_time is set, silent duplicates when it is not,
which is the live configuration.

Section 5 of the spec already read "only after every batch that input
produced"; the implementation took that as EVERY batch. The correct reading is
ITS OWN, and section 5 has been rewritten so it cannot be read the other way.
Two lists decide it: the inputs contributing a document to the batch currently
open, and the inputs read to the end whose last documents are still in it.
Closing a batch flushes the intersection; an input contributing to no open
batch is renamed as soon as it has been read. The contributor is recorded
BEFORE the write, so a document closing its own batch under ROLL_THEN_ALONE
still attributes that batch. Every close goes through one closeBatch helper
and the rename is downstream of it, so .done continues to mean delivered.

2. The executor had no designer panel. It was registered in the executor
dropdown but had no branch of its own, so an elarxml step fell through to the
generic external one: name/value param rows and a disabled Script field. Added
a dedicated branch on the sqlreport model - the six required parameters plus
three subsections carrying every optional parameter of section 8, each with
the executor's own default as its placeholder. clientValidate names all six
missing parameters in ONE message, as the executor does, and refuses a
multi-character separator or quoteChar because both are read with charAt(0).

maxBytesPerBatch and oversizeDocumentPolicy stay VISIBLE under
batchBy=DOCUMENTS, labelled "NOT in effect", rather than hidden: the step log
already names the ignored limit with its value for the same reason. A field at
its default writes no parameter at all, so the defaults stay in the executor
instead of being frozen into every workflow XML.

buildXml needed NO change: every field is a step <param>, which it already
emits generically. This is not the reportQuery case. Checked rather than
assumed - those assertions pass against the unpatched file too, which is the
proof. variables.html gained the matching PARAM_OPTIONS entries, so a
parameter offered as a dropdown in the designer is not a free-text box in the
mass editor.

OPEN, deliberately not changed in this commit
- max.line.length from the properties file is read, LOGGED and then ignored.
  ElarRun:104 resolves it, but Batch.open and the PULL writer recompute the
  width as maxLineLength > 0 ? maxLineLength : 20000 without the config, so
  every INDX is wrapped at the hardcoded 20000 whatever the family declares.
  Measured: a family declaring 25000 logs 25000 and delivers 20000, so the
  step log states a width the bytes do not have. Section 8b's 25000 fallback
  never reached the code either. One line to fix, but it moves the line breaks
  of every delivered INDX on the first run after deploy, so it needs its own
  batch and an explicit decision.
