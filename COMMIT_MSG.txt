Built-in ${parentId}: the id a versioned feed descends from

First batch of section 2 of .claude/SQLREPORT_VERSIONING_VARIABLES.md. Only
the built-in variable; the structural-change detection and the
version/overwrite dialog are the next batch.

VarResolver.parentId(feedId) strips ONE trailing .v<digits>, so tf0003819.v2
gives tf0003819. The derivation is textual and TOTAL: on a feed that is not a
version it returns the feed id unchanged, so ${parentId} is never empty and a
query, a path or a report can use it unconditionally without its author
knowing whether that particular feed happens to be a version. That is the
whole reason it is a variable and not a UI label. Only the last suffix is
stripped (tf0003819.v1.v2 gives tf0003819.v1), x.v with no digits is not a
version, .v1 would strip down to nothing so it is returned unchanged, and null
or blank give the empty string rather than null. Companion isVersioned() for
the UI batch.

Published in all six places ${feedId} is: WorkflowEngine.buildRun run
variables, both design-time preview maps in ApiController (feedVars and the
csvsql preview), the tag-resolution map used by Operations, and in
designer.html both the Builtin-vars cheat sheet and the path autocomplete
list.

Verified rather than assumed: the spec DECIDED that tf0003819.v1 is an
acceptable feed id so the registry stays untouched, and that now holds against
the code - every place a feed id is validated (WorkflowXmlParser:65,
ApiController:1806 and :2321, clientValidate twice in designer.html) uses
[A-Za-z0-9._-]+, which already admits a dot. No change was needed anywhere.

Why this batch first: ${parentId} is the only part of section 2 that is
provable in isolation, changes no behaviour, and is useful on its own - an
author can start writing ${parentId} into delivered file names before any
version exists, because on an unversioned feed it equals ${feedId}. Shipping
it separately also means the risky part of section 2 arrives on a codebase
where the variable is already deployed and observed.

Decision recorded here, left open at the end of the previous batch: the
versioning trigger will apply to the DESIGNER SAVE ONLY, not to the
Variables-page bulk add. The reason is arithmetic. A version is created
scheduling-inert and the original keeps its schedule, so triggering it on a
bulk add across forty feeds would produce forty new unscheduled workflow ids
and change nothing about what runs tonight - the operator's intended change
would simply not happen, and there would be forty workflows to clean up. A
version is an interactive, one-feed-at-a-time decision by the author; a
fleet-wide add is a deliberate operation where the operator has already
confirmed PROD inclusion in the dialog. The bulk-add confirmation text must
say plainly that it modifies the feeds in place and creates no versions, which
folds into the next batch.

Verified: parentId and isVersioned were transcribed verbatim, compiled with
-source 8 and run against 18 assertions - unversioned returns itself, null and
blank give the empty string, .v1 and .v12 and .v0 all strip, only one suffix
strips, surrounding whitespace is trimmed, and x.v, x.V1, xv1, tf.0003819, .v1
and a bare dot are all correctly NOT treated as versions. Brace and paren
balance is 0/0 on the three Java files, the import checker is green on every
added line, and node --check on the designer's inline JS passes with zero
literal newline/CR escape sequences and only the pre-existing commented
Thymeleaf marker.

NOT verified: mvn clean package, and ${parentId} resolving inside a real run.
