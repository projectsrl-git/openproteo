elarcheck batch 0: specification, written from the reference scripts

Specification committed at .claude/ELAR_CHECK_EXECUTOR.md, self-contained. No
implementation.

The executor is read-only and is built before the generator on purpose,
because it is the acceptance harness: the decisive criterion for elarxml is
that a regenerated file passes every check here while the original does not. A
regeneration that reproduces the original's defects has reproduced the wrong
thing.

The five reference scripts are in the htmlviewers repository rather than this
one. They were read, and they answered the three points this spec first listed
as open - two of them differently from what the descriptions alone implied.

Lines are one-based and the declaration line counts like any other, but the
number reported depends on the finding: a line break is reported at lineNo
minus one, the line where the break starts and which has to be repaired, while
an invalid space after an angle bracket is reported at the current line.
Reporting both at the current line would have put every break one line late,
and the definition of done requires the numbers to match what the scripts and
ELAR reported.

The record ordinal accumulates document starts across the whole file and never
restarts, so it is the count of documents begun so far and is zero before the
first one. The loop adds the current line's document starts between the break
checks and the bad-angle check, so two findings on the same physical line can
legitimately carry record numbers that differ by one. That is worth knowing
before it looks like an off-by-one.

Twenty-five thousand is the default and the agreed target; thirty thousand is
what the receiver actually enforces, by horizontal truncation. So the message
has to separate over target from would be truncated, or a line at twenty-seven
thousand reads as fatal when it would still arrive.

The scripts also carry a distinction the prompt's description did not. A break
inside markup and a break inside a value are reported as different kinds,
separated by whether the previous line ended inside a tag, because they need
different repairs - and the script's own comment records a defect it once
caused: rejoining a markup break by inserting a space is correct only where
the break fell between two attributes, and anywhere else, after an opening
angle bracket in particular, it produces an invalid element start, which is
exactly what another check exists to find. This checker never repairs
anything, but it reports the two kinds separately so that whoever does knows
which repair applies. The payload is excluded by tracking the current
element's local name across lines, prefix ignored, rather than by any
heuristic on line content.

Two design points decide the shape of the implementation and are settled in
the spec. There are two physical passes over each file rather than one,
because the textual checks need physical lines and must keep going after the
document stops being well-formed - which is the point of reporting every
occurrence when the parser stops at the first - while the structural checks
need the parser, and sharing one reader fails on both counts. And StAX
coalescing must be off, because it would materialise a payload of tens of
megabytes as a single string, the exact accumulation that killed the legacy
generator; the line-break check therefore tests each character fragment rather
than assembling the value, which is equally sensitive and needs no memory.

Read-only is made verifiable rather than promised: no write API may appear in
the package, asserted by a build scan, and the findings file is written to the
step directory and never to the inspected one.

NOT verified: nothing to verify, this batch is a document. What is needed
