elarxml: the hash tag was hardcoded, and one figure is a guess

Two follow-ups on the finished executor, both found by reviewing it rather
than by anything failing.

ElarRun carried a constant naming the digest element, while the content and
DSAK tags were already read from the properties file. That broke the rule this
spec itself sets out - no family's tag name anywhere in the code - and it had
a concrete consequence: for any family whose template calls that element
something else, the digest would have been written nowhere at all, silently,
since the run would simply have found no tag by that name. Every family except
the one whose template has been read is in that position.

output.hash_tag now sits beside output.content_tag and output.dsak_tag,
defaulting to this family's name so no existing properties file needs editing.
No ELAR literal remains anywhere in ElarRun, and the rule scan asserts it.

It is verified by running the whole executor for a family that shares no tag
name with this one - the block, the id, the constant, the digest, the kind and
the body all called something different. The digest lands in that family's own
hash tag and equals the SHA-256 of the source file's raw bytes, the extension
lands in its own kind tag, the payload decodes back to the file byte for byte,
the family's own constant survives from the template, and the word ELAR
appears nowhere in the output.

The second follow-up is a disclosure rather than a change.
PER_DOCUMENT_OVERHEAD, the allowance for tags and line separators on top of
the Base64, is the one figure in this executor that is chosen rather than
derived from something. It is unused entirely under the default batching rule,
and under the byte budget it only shifts the rollover point by a couple of
kilobytes per document, so it cannot corrupt anything - but it is a guess and
the code now says so. estimateDrifted already compares it against the bytes
actually written for every document and logs when the two come apart, so a
wrong figure reports itself on the first real run. Correct it from that log
rather than from another guess.

The lesson worth recording is that a rule written into a spec does not enforce
itself. The scan for family literals covered this package from the start, but
I had put the tag name in a named constant rather than in a comparison, so it
read as ordinary code and the scan had nothing to object to. Scans catch
shapes, not intentions.

NOT verified: mvn clean package, and any of this against real data. This
change touches only the elar package, which compiles and runs here; the eight
suites pass, including the new one.
