elarxml batch 6: the run loop, and registration in five places

The executor itself, and the wiring that makes it reachable from a workflow.

ElarRun holds the run loop and stays free of Spring and of the orchestrator's
own types, exactly as the rest of the package does. That is not tidiness: it
is what allows the whole executor to be exercised end to end against real
files on disk in a test, rather than only on deploy. runElarXml in
InternalSteps does two things and nothing else - translate step parameters
into options, and translate counters back into run variables.

IndxTemplate needed a streaming form. The one-call write, which takes a list
of documents, would have meant building the list of a batch's documents before
writing any of them, and that is precisely the accumulation this rewrite
exists to remove. Prologue, each document and epilogue are now separate calls,
and the caller decides how many documents go between them.

Registration is in five places rather than four: the parser whitelist, the
parser's own error message, the parser's internal set,
WorkflowEngine.internalKind, the InternalSteps dispatch, and the designer
dropdown. The error message and the dropdown are the two that get forgotten,
and the reportQuery defect earlier in this project was exactly a preview that
disagreed with the writer.

Every missing required parameter is named in one message. An operator
configuring a new feed should not have to run the step six times to be told
six things.

Verified with 39 assertions across two harnesses. End to end against real
files: five documents in three batches, filenames sixty seconds apart, each
INDX parsing as XML with its prologue, its template constants, its mapped
values and an uppercase DSAK. The load-bearing assertion is that the digest in
the delivered INDX matches the SHA-256 of the source file's raw bytes, and
that the embedded Base64, decoded, hashes to that same value - so the file
that went in is provably the file that came out. Then: the PULL referencing
its own INDX by name; the input renamed only after delivery; a missing content
file refusing the run with the output directory untouched and the input
unrenamed; batching by BYTES with the ignored max_index_docs named in the log;
an oversize document alone in its batch; validate off by default and reporting
when on; an empty input directory saying so rather than succeeding quietly;
leftover out_ intermediates ignored; an existing final name refused with
neither a PULL nor a .part left behind; a mapped tag missing from the template
warned about; and no row content anywhere in the log. Separately, runElarXml
was extracted and run against stubs of the real signatures: all six missing
parameters in one message, a partial configuration naming only what is
actually missing, and a failure inside the run reported through the step log
rather than thrown at the engine.

One of these tests caught a real behaviour I had documented but not pinned.
With output.start_time set explicitly the synthetic clock restarts at the same
value, so a same-day re-run produces colliding filenames and the run is
refused on its first batch rather than replacing a file that may already have
been delivered. With start_time unset the clock takes the wall time, a re-run
produces new names, and duplicates accumulate quietly - which is what the
same-day warning covers. Both are now separate assertions rather than one
assumption, since which of the two applies depends only on a line in a
properties file.

NOT compiled, and this is the honest limit of this batch: InternalSteps,
WorkflowXmlParser, WorkflowEngine and designer.html need the full Spring tree
from the internal Nexus, which the sandbox cannot reach. They were checked
structurally instead - brace and parenthesis balance, every helper and field
verified against its real declaration rather than assumed, no name collision
on the two helpers added, and the designer line checked for literal
backslash-n, for the Thymeleaf markers and for anything the corporate proxy
rewrites. mvn clean package is the gate before this is deployed, and it is the
first thing to run.
