ftpsend batch 3: the executor, its six registrations, the panel

The step becomes reachable. Six registration points, read at 1be571f and not
remembered: WorkflowXmlParser lines 89, 91 and 94,
WorkflowEngine.internalKind, the InternalSteps dispatch chain, and the
designer dropdown. Plus the <send> parsing, SendSpec in the model,
FtpTargetStore, the ftp-targets-file property, a read-only /api/ftp-targets,
and the step panel.

The panel is the first reorderable list in a step panel: masks are added,
deleted and moved with UP and DOWN, reusing the .mv buttons the node header
already has. The order of the rows IS the send order, and the panel says so,
because it is the only thing that decides whether the file announcing a
package as complete goes last.

Two defects were found by the tests rather than by review, and both would have
been invisible in a code read.

The first is the one that matters. StepExecutor.Result starts its exit code at
-1, not 0, so the failure branch as first written - exitCode == 0 ? 1 : keep -
left it at -1, and the normalisation at the end of the method turned that into
0. A delivery that failed verification was reported as a successful step. The
test that caught it is the one where the server reports a SIZE one byte short.

The second came from a mutation that returned green: treating directories as
sendable files changed nothing, because no test directory had a subdirectory.
A catch-all mask claiming a folder would have gone unnoticed until a real
packaging directory happened to contain one. A case was added and the mutation
now fails.

A third gap turned up on the panel side, also from a green mutation: buildXml
sorting the masks instead of preserving their order produced identical XML,
because the two masks in the test were already in alphabetical order. The rows
are now put in a deliberately non-alphabetical order before the XML is
checked.

VERIFIED
- 49 executor assertions green on Java 8, the production runtime, and on Java
  21. They run runFtpSend itself: the method and its helpers are extracted
  from InternalSteps.java by line range and diffed against the source, so what
  is exercised is byte-identical to what ships, not a transcription. It is
  driven against the FTPS server written for batch 2, with the five real file
  names of 40_PACKAGING including the .control at zero bytes.
- 11 executor mutations, 11 caught, after two came back green and were
  investigated - one malformed, one a real gap.
- 42 designer assertions green in jsdom, against the real template. Every
  control is driven by dispatching an event on the rendered element, never by
  writing to wf.nodes: a test that edited the model behind the panel could not
  see a control that stopped redrawing, which is the defect this file exists
  for. Add, delete, both reorder directions, the no-op at each edge, the
  checkboxes, validation and the generated XML.
- 12 designer mutations, 12 caught. Removing renderNodes from moveSend and
  from delSend both fail on the panel assertion and not only the model one,
  which is the point.
- The Windows half of the mask path check now has a case of its own. It had
  none: the forward-slash test passed either way, and a mutation dropping only
  that half went unnoticed until the case was added.
- Patch applied on a second clean clone at 1be571f, compared byte for byte,
  and both suites re-run from the applied tree.

NOT VERIFIED
- mvn clean package. Maven Central is unreachable from the sandbox, so the
  full tree cannot be compiled: Spring, Jackson, POI, H2 and jt400 are absent.
  What was compiled is the ftps package, model/def, AppProperties,
  VarResolver, RunControl, StepExecutor and the extracted executor, against
  minimal stubs for the four annotations and types they touch. The edits to
  WorkflowXmlParser, WorkflowEngine and ApiController are therefore NOT
  compiled anywhere: they are three small, mechanical changes, and they are
  the risk this commit carries.
- FtpTargetStore reads and writes JSON through Jackson, which is stubbed here.
  Its map behaviour is exercised; the file round-trip is not.
- Nothing has been sent to a real server, and the network path is still what
  section 2 of the specification says it is.
- The targets admin page and USAGE.md remain batch 4. Until then a target is
  created by writing ftp-targets.json by hand.
