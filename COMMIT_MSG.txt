elarxml batch 5: the validate checks, and the one that could not exist

The checks the legacy Validator was supposed to perform and never did, off by
default.

Why it never ran is worth repeating in the code, and is: CsvValidator.validate
began by requiring four columns, the vertical intermediate it was handed has
three, so it returned immediately and silently before any check executed.
Every delivered INDX went out unvalidated.

Two of the three checks are reproduced. The third is not, and that is the
substantive decision in this batch. The reference check compared the document
id against the value of the tag that doc_id_reference maps to. On a vertical
intermediate those were different things; on a flat row they are the same
value by construction, because the document id is the value of the column that
maps to that tag. The check can therefore never fail. A green check that
cannot go red is worse than no check at all, since it reports confidence it
does not have, so it is replaced by the invariant that survives the
translation and can still fail on real data: the document id must be present
and non-empty. Section 10 of the spec now records this rather than leaving the
original wording to be implemented literally by whoever picks it up next.

Two reporting decisions are worth stating. A duplicate document id names the
id, because it is a document identifier and is what an operator needs in order
to find the row - the same class of value the pre-scan already reports for a
missing content file. A duplicate value on any other tag names the tag and the
line numbers but never the value, because an arbitrary tag can carry anything
at all and the tag plus the line number is enough to act on. Findings are data
rather than errors, so nothing here throws, including on a null row.

Memory is two sets of small keys: the document ids, and one value set per tag
named in not_duplicated_tags_list. That is bounded by the document count and
by nothing about content size. At a few thousand documents it is nothing; at
tens of millions it is not, and the spec says so explicitly, because the point
at which this needs revisiting should be written down rather than discovered
as an OutOfMemoryError.

Verified with 30 assertions compiled with --release 8 and run: a clean file
saying so rather than staying silent, which is the whole point of running a
check; the duplicate id flagged on the second occurrence with the id named; an
empty, absent or whitespace-only id caught and not also counted as a
duplicate; duplicate tag values naming the tag but not the value; absent and
blank values not counting as duplicates of each other; values compared
trimmed, as the map lookups are; the listing capped at twenty with the count
left uncapped and the message saying how many more; the message reporting that
no not_duplicated_tags_list is configured rather than looking as though the
check passed; a repeated tag in the list collapsed; and a null row handled
without an exception. The batch 1 to 4 suites were re-run and pass.

Two assertions failed on the first run and both were mine rather than the
code's: the test helper put the document-id tag into the unique-tag list as
well, so two checks legitimately fired where the assertion expected one. They
are isolated now, and the two-checks case is kept as its own deliberate
assertion so the behaviour is pinned rather than merely avoided.

NOT verified: mvn clean package, and the checks against real data. Worth
running once with validate=true on a feed already delivered before turning it
on anywhere: these checks have never executed, so whatever they find has been
in production for as long as the feed has.
