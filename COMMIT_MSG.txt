elarxml IFS content, batch 0: specification, written from the existing code

Specification committed at .claude/ELAR_XML_IFS_CONTENT.md, self-contained. No
code in this commit.

No Gate 0 on Nexus: JTOpen is already a declared dependency,
net.sf.jt400:jt400:20.0.7, and IfsSupport already uses AS400, IFSFile and
IFSFileInputStream.

THE CONSTRAINT THAT SHAPES THE DESIGN

The elar package is free of Spring and compiles standalone with javac
--release 8. That is what has allowed every suite in this subsystem to run the
real executor against real files in a sandbox, and it is what caught the .done
rename defect, the value-edge breaks, the split start tag and the counter that
counted twice. IfsSupport is a Spring component in the ds package. Making elar
depend on it would leave the whole subsystem testable only against a live
AS/400.

So: a JDK-only ContentStore interface inside elar, LocalContentStore beside it
reproducing today's behaviour, and IfsContentStore in the engine layer where
Spring and JTOpen already live, constructed by runElarXml and passed in. elar
stays standalone-testable in full; only the thin adapter is not, and that is
declared rather than implied.

TWO PASSES OVER A NETWORK FILE

The template places the hash element before the content element, so the digest
must be known before the payload is written. Locally that is two sequential
passes, neither holding the file. Over IFS it is two network transits.
Buffering the payload to get one pass is precisely the ByteArrayOutputStream
that produced the 147 MB batches and the OutOfMemoryError, so it is rejected.

Recommended instead: stage each document to a local temp file once, then
digest and encode from local disk. One transit, the streaming invariant
intact, peak local disk one document rather than one batch - and the
size-and-modification stamp becomes meaningful, because a local temp file
cannot change underneath us while an IFS file can.

THE PRE-SCAN

It has to stay: IfsSupport.copyListToLocal decides against a pre-scan and its
own javadoc says why ELAR is different, since a partial set beside an unmarked
input is unrecoverable. But a per-row existence check is a network round trip
each. Resolution: list the IFS base directory once, which yields name, size
and modification time for every entry, so existence, length and the DSAK
extension all become local lookups and the byte-budget estimate gets real
sizes. The listing is held for the run, so it needs a declared cap rather than
a discovered OutOfMemoryError.

buildXml DOES NEED A CHANGE THIS TIME

The datasource is a step ATTRIBUTE, not a param: runIfsCopy reads
step.datasource and looks it up in the registry the sql steps use. Every
previous elarxml field was a param, which buildXml emits generically. This is
the reportQuery case, and the earlier note that buildXml needed no change does
not extend to it. The parser must also carry datasource for an elarxml step,
and clientValidate must require it when contentSource is IFS.

OPEN, AND NOT MINE TO DECIDE

Four decisions are listed in section 8. The one that changes the most code:
does the CSV column carry a bare file name or a full IFS path? Today the value
is reduced to its last path segment, mirroring the legacy updateFilePath. Over
IFS a full absolute path is far more plausible, and if the feed carries one
then the current rule discards the only part that matters and every row lands
in the discards file with the file sitting right there. It should be answered
from a real feed rather than assumed, and batch 1 waits on it.
