Contract: the delivery filename carries the commit it was generated on

A zip delivered from chat is now named openproteo-<topic>-<base>.zip, and the
patch inside <topic>-<base>.patch, where <base> is the short hash of the
commit the patch was generated against. This delivery is named that way
itself.

The reason is the deploy script: it picks the most recent zip in D:\\downloads
and has no way of knowing where that zip came from. With the commit in the
name the check before launching is a single glance - run git rev-parse --short
HEAD, compare it with the suffix, and if they differ the patch is on a
different base and should be regenerated rather than applied.

This has now happened twice in this project, both times because main had moved
between my reading it and my generating the patch. In both cases git apply did
its job and refused, so nothing was corrupted, but the discovery came after
the attempt rather than before it. The name moves it earlier.

It also works in the reassuring direction: if the suffix matches but the zip
looks old, it is the same patch, and applying it again is harmless.

The rule for whoever generates the patch is that the suffix is written after
reading the HEAD of the clone, never from memory - which is the same
discipline the contract already requires for generating on a fresh clone in
the first place.
