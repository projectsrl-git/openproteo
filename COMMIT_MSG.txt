elarxml IFS content batch 1: the ContentStore seam, proved a no-op

Answers section 8a of the specification and delivers the refactor it was
blocking. The CSV column carries a FULL IFS path, so sections 3, 4 and 6 are
revised and batch 1 is written against the corrected design.

RESOLUTION MOVES INTO THE STORE, AND THE TWO STORES DELIBERATELY DISAGREE

LocalContentStore keeps today's rule exactly: trim, take the last path
segment, join it to the family's documentPath, so a traversal still cannot
escape. An IFS store will take the value as given, joining contentIfsPath only
when the value is not absolute.

The asymmetry looks wrong until you see why it is right: it is one CSV serving
two topologies. Under LOCAL an ifscopy step has already copied the documents
down, flattening whatever tree they came from into a single directory, so only
the file name can still be meaningful and taking the last segment of the IFS
path is exactly correct. Under IFS the tree is still there and the path is the
only thing that finds the file.

The answer also removed a trap that would have been silent. Under a shared
last-segment rule an IFS run would have reduced every full path to its file
name, looked for it under a base directory it is not in, and sent every row to
the discards file with the documents sitting untouched on the IFS - reporting
itself as a clean skip of everything.

Section 4 is revised too: listing one base directory no longer works, since
with a path per row the documents can be spread over many directories. The
pre-scan will list the distinct PARENT directories instead, derived from the
CSV itself, which is a handful of round trips for a feed of thousands of rows.
With a guard for the degenerate case: if the parents outnumber half the rows,
listing each is worse than asking per file, so the store falls back to
per-file existence and logs which strategy it chose. A run that silently took
the slow path is one nobody can explain afterwards.

BATCH 1

ContentStore and LocalContentStore in the elar package, JDK only, and every
use of the content file routed through the interface: the pre-scan's existence
check, the byte-budget size, the DSAK name, the digest pass, the encode pass
and the change stamp. ElarPreScan.resolveContentFile is gone; its rule now
lives in LocalContentStore.resolve, where the other store can differ from it.

The seam is inside elar on purpose. That package is free of Spring and
compiles standalone under --release 8, which is what allows the whole executor
to be executed against real files in a test rather than only inspected, and it
is what caught the .done rename defect, the value-edge breaks, the split start
tag and the counter that counted twice. IfsSupport is a Spring component, so
the IFS implementation will live in the engine layer and be passed in.

DEFECT FOUND BY THE SEAM TEST, NOT BY REVIEW

Nothing closed the store. With a local store that is harmless; with an AS400
connection inside it is one leaked per run, which is the kind of problem that
only surfaces after a week of retries. ElarRun now closes it in the finally,
on every path including the failing ones, and the interface documents that the
executor owns the store for the duration of a run. A Closeable in an interface
is a claim; something has to call it.

VERIFIED
- Proved a NO-OP the only way that means anything: byte for byte. The same
  fixture - 50 documents, full IFS paths in the column, accented metadata -
  delivered before and after the refactor, and the SHA-256 of the delivered
  INDX and PULL compared with formatting on and off. Identical on both sides.
  Assertions alone would not have carried a no-op claim; digests do.
- All five existing elar suites pass unchanged: 19, 31, 15, 36 and 33
  assertions.
- 23 new assertions with a fake store, which is what batch 2 depends on: the
  store's own resolution rule is the one used and a full path is kept whole;
  LocalContentStore still takes only the last segment from a bare name, a full
  IFS path, a Windows path and a traversal; a document the store does not have
  is skipped and copied to the discards file; length, lastModified and two
  separate streams are all asked of the store; and a read failing part-way
  through, as a dropped connection would, aborts the batch with no INDX
  delivered, no temp file, no .done rename and no discards file published.
  documentPath in that fixture points at /nowhere/at/all on purpose, so a run
  driven by another store must never touch it.
- Package rule scans clean.

NOT VERIFIED
- mvn clean package: Maven Central is unreachable from the chat sandbox, so
  the build on the target machine remains the only final proof. The elar
  package compiles and runs standalone in full.
- There is no AS/400 in the sandbox and there is no IFS code in this commit. A
  fake store proves the seam; it cannot prove JTOpen. The honest sequence
  stands: this batch deployed and proved a no-op on a real feed first, then
  IFS on one family with a small input, then volume.
