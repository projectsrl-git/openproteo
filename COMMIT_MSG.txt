tiffcompress batch 1: the scanner, and a scan blind to its own panel

The executor, mode=SCAN only. It reads the TIFF header and follows the IFD
chain to enumerate pages, never reading pixel data, and reports the
distribution of compression tag 259 by file count AND by bytes together with
how much of the corpus could be re-encoded to CCITT T.6. mode=COMPRESS refuses
with an error rather than quietly scanning instead.

Two packages, one executor. orchestrator.tiff carries no write API and
tools/scan_tiff_readonly.js asserts it, which is the elarcheck property that
makes a scan safe to aim at a live directory. The report is rendered by the
package and written by InternalSteps, for the same reason. Everything that
writes will live in orchestrator.tiffpack.

The sample is the deliverable, not a preview: the number exists to decide
whether a compressor gets built. RESERVOIR is the default - one lazy pass,
unbiased, opening no more files than the alternative. DIRECTORY samples a
prefix of the enumeration, which is a corner of the store rather than a sample
of it; its only advantage is that the walk stops early, and both the panel and
the step log say so when it is selected. The report header carries the order,
the seed and both counts, so a percentage cannot travel without the method
that made it.

THE REDRAW SCAN WAS BLIND, AND IS NOW CALIBRATED
Open item 5 was that scan_panel_redraw.js had never been calibrated against a
panel written after it. This is that panel, and the calibration found two
defects in the SCAN rather than in the panel. It recognised only var x =
nodeParam(n,'p') === and not the || 'DEFAULT' idiom, so it never saw the new
controls at all; and it recognised a redraw only inside a named helper, not
one written into the attribute. A mutation removing a redraw was caught by the
jsdom suite and NOT by the scan. Both patterns extended. The inline one had to
be bounded to its own attribute: unbounded, it ran forward past the handler it
started in and credited directory and maxFilesScanned with a redraw they do
not have.

A PROXY MEASUREMENT THAT LIED
The first sampling-bias scenario assumed the walk would return the first-named
files first. Measured: Files.newDirectoryStream on ext4 returns hash order -
15 of the first 100, not 100 - so the scenario passed for DIRECTORY by
accident and proved nothing. Node's readdir had reported name order because
libuv sorts with alphasort and Java does not. The suite now demonstrates the
bias through the walk's own FIFO ordering over directories, which this code
owns and no filesystem can change.
