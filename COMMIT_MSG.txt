Standalone viewers: remember relationships, and share one link core

Two things, both groundwork for the CSV and in-app batches.

Declared relationships are now remembered. Declaring a set of them is real
work, and on a workspace that is re-opened every day it is the same work every
day, so they are kept in the browser under op-viewer-links-v1 and restored
when the same files are added again.

What is stored is only the declaration: file names, entity-list paths and
field names. Never a value, never a row, never a parsed document. In a Legal
Archive context that distinction is the whole point, so it is asserted rather
than assumed - the test checks that no identifier from the data appears
anywhere in what was written.

Files are matched by name, because an id only means something inside one
session. A renamed file is therefore a forgotten file, which is deliberate:
matching on anything looser would restore a declaration onto a file that might
not be the same one. A saved relationship whose two files are not both open
simply waits, and comes back when the second one arrives. One whose entity
list or field no longer exists is reported and skipped rather than silently
ignored - a file that changed shape under a saved declaration is exactly the
thing an operator wants to hear about, and silently skipping it looks
identical to the cache having been forgotten. It stays remembered in case an
older version of the file comes back. Closing a file drops the live
relationship but keeps the saved one, since the file will very likely be
opened again tomorrow. Forget saved relationships clears the lot. Storage
being blocked, as in a private window, must not break the page, and that is
asserted too.

The second change is groundwork rather than a feature. The link layer no
longer knows what a file is: it asks the file, through three methods - the
entity lists it offers, a way to iterate one field, and a way to turn a
reference into an entity. The index stores those references rather than
materialised entities, which is what will let a CSV of a hundred thousand rows
be indexed as an array of integers instead of a hundred thousand objects. The
JSON page now supplies that adapter, so when the CSV page arrives there is one
implementation of relationships, indexes and the diagram rather than two
copies drifting apart.

Verified with 24 new assertions driving the page through simulated reloads
with a shared storage: two relationships declared in one session, both written
keyed by file name and containing none of the data; a second session restoring
the self-link on its own and the cross-file one only when its second file
arrives, after which the cells are clickable again; a file whose shape changed
being reported and skipped while the declaration stays on disk; a renamed file
restoring nothing; closing and reopening a file restoring it again; Forget
clearing storage; and the page still booting with localStorage throwing on
access. The three earlier suites were re-run against the refactored core and
pass unchanged.

One defect worth recording. A duplicate cache implementation nearly shipped:
page.js already had one and a second was injected into the same scope.
JavaScript allows duplicate function declarations and the last one wins, so
nothing failed - node --check passed and all three suites passed. A duplicate
top-level function scan is now part of the checks for these single-file pages,
since assembling a page from parts makes exactly this mistake easy and
invisible.

NOT verified: the cache in a real browser, where localStorage is per-origin
and a file:// page has its own rules. Declare a relationship, reload the page,
add the same file and it should come back.

The CSV viewer is the next batch on its own. It has to go INTO the existing
csv-viewer.html, which carries a virtual-scrolling grid, column filters,
aggregation and displayschema handling, and retrofitting tabs and
relationships around that without breaking it is a job worth its own patch
rather than a hurried addition to this one.
