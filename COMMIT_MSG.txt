objunpack: the core classes, unwired (batch 1)

A Transarch object package back to its objects under their original
names and its metadata CSV byte for byte. Plain classes: no executor
name, no dispatch, no panel yet, so nothing an existing workflow does
can change.

- objunpack/ObjectUnpack: checksum, one pass into a staging folder,
  the join audit.json x metadata.csv, the package checks, rename,
  commit. Extraction, name rules and limits are unarchive's; checksum
  and name grammar are objpack's; the CSV reader is filerename's.
- SubmissionName.parse: the inverse of archive(). Added, nothing
  existing changed.
- AuditJson.read: a strict JSON reader that takes each item by key, so
  PowerShell's formatting and key order do not matter. write and
  validate, which objpack uses, are untouched.
- EntryName.printable made public (one word).

Gate 0: G2 answered - names may repeat - so the refusal reports every
clash. G1 and G3-G8 follow the spec's recommendations, to be confirmed.

Found by measuring: under an ASCII locale an accented file name cannot
be created (Java 8 and 21); it is now refused naming the encoding and
the remedy. The spec is corrected where the code proved it wrong, with
the old text struck through; section 13 is the as-built.

Verified on Linux (sandbox; Temurin 1.8.0_432 and JDK 21.0.10 both
run, Java 8 javac; root and uid 65534; LANG=C.UTF-8 and empty): suite
green in all eight combinations, 638 assertions under UTF-8 and 179
under ASCII, plus 7 only a non-root user can observe; 44 packages, 21
from the real ObjectPack and the legacy script under pwsh, 23 rebuilt
from real members with GNU tar; round trip on ten packages of both
producers; 56 mutations on copies, 55 caught, 1 equivalent; git apply
--check on a second clean clone.
Verified on Windows: nothing. Windows name rules ran on Linux with the
host named: the logic, not the platform.
Not verified on either: mvn clean package; Windows PowerShell 5.1; a
legacy package made on Windows; size and timing at 100 000 objects.
