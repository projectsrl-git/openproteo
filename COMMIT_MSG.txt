Mask address prefix: batch 2 specification, no implementation

Spec at .claude/MASK_ADDRESS_PREFIX.md, self-contained. No code in this
commit. Batch 1 (1b08084) shipped the international street and city pools;
this decides how the hardcoded "Via " stops being hardcoded.

RECOMMENDATION: a step parameter, and it should carry a FORMAT TEMPLATE
rather than a bare prefix. Default "Via {street} {number}".

Four options were evaluated and two of the three rejections turned on a
measurement rather than on taste.

A bare addressPrefix parameter is rejected on a reading of designer.html:499
- setNodeParam DELETES a parameter when the value is empty and never creates
  an empty one, so from the designer "present and empty" cannot be
  expressed and "no prefix" is unreachable. That is the setting that cannot
  take effect, refused three times before in this codebase. The escape hatch
  would be a magic token. A bare prefix also cannot reach Oakwood Street,
  Bahnhofstrasse or Damrak, because the constant sits in PREFIX position -
  four of the seven provenances now in the pool file.

Baking the type word into the pool VALUES is NOT rejected on byte-identity:
measured, it reproduces the baseline digest exactly, since the pool keeps its
length. It is rejected on the failure mode. The pools page exists so an
operator can replace a pool, the documented format is the bare name, and a
bare-name replacement would silently turn every address into "Botticelli 90"
with no error and no counter. It also inverts the rule batch 1 wrote into
both file headers one commit ago, and it ends the freedom to mix an Italian
pool with a French prefix.

A "#prefix=" directive in the pool header is rejected on the compatibility
direction: a "#" line is by the format's own contract IGNORED, so a newer
pool file read by an older build produces "Via Voltaire" silently, and
external pool directories are shared across installations that are not
upgraded together.

VERIFIED (9 assertions, javac --release 8, real MaskEngine/MaskPools/
MaskGenerators, 2000 values per measurement)
- Stream.nextInt(bound) rejection-samples ON THE BOUND. Windows: 16 of 2^32
  at bound 60, 57 at 61, 46 at 250. After nextInt(60) and nextInt(61) on the
  same seed the next byte was identical 2000/2000, so consumption is
  bound-independent in practice but not by construction, and nothing
  proposed here changes a bound.
- A pool one entry longer moves the drawn index for 1962 of 2000 values. It
  is the index that moves, not the stream position.
- The recommended design renders SHA-256 284b372f7a589eb875c25faa9fd16a546
  83045793a40e9a6cd8ad1cc59c76f8d at the default template, which is the
  digest of the shipped address() over the same 2000 values. The stream is
  then probed one byte further and matches 2000/2000 - a measurement of the
  stream POSITION, not an argument about it.
- Registration read rather than predicted: WorkflowXmlParser:175-176 and
  WorkflowXmlWriter:204-207 handle every <param> generically, and
  designer.html:444 does the same in buildXml. No parser, writer, DTO or
  buildXml change is needed. This is the elarxml <param> case, not the
  reportQuery new-element case.

RECORDED BECAUSE IT WAS GOT WRONG ONCE
The first run reported the two decisive measurements as FAILING. The harness
was wrong, not the code: it seeded the stream with the raw value while
MaskGenerators seeds it with norm(value), upper-cased under the default
trimUpper. Taken at face value it would have argued against the recommended
option on false evidence.
