sqlreport executor (batch 1): read-only queries, Markdown evidence

Implements batch 1 of section 1 of .claude/SQLREPORT_VERSIONING_VARIABLES.md:
a new internal executor that runs a LIST of read-only queries against one JDBC
datasource and writes a single Markdown evidence report. No CSV and no data
file: the report is the deliverable, so it can be attached to a
reconciliation.

Registered in the four locations the project's rule requires - the exec
whitelist AND its error message in WorkflowXmlParser, the parser 'internal'
set, WorkflowEngine.internalKind(), the InternalSteps dispatch - plus the two
designer ones, the executor dropdown option and clientValidate. Missing one of
these is what makes an executor invisible in the dropdown.

Storage is one <reportQuery> element per query, never a delimited string, so a
';' inside a statement cannot corrupt the definition. The element is NOT
<query>: that tag is already the single-statement child of the sql executor
(textOrAttr(el,"query") looks for a child before the attribute), so reusing it
would have made the first report query silently become StepDef.query. New
model/def/ReportQuery, StepDef.reportQueries, parser and writer round-trip,
NodeDto.ReportQueryDto and the toDto mapping.

Read-only is enforced at two levels, both before anything is executed. New
engine/SqlReportSupport - deliberately free of Spring, JDBC and project types,
so the part whose behaviour must be provable without a database compiles and
runs on its own - strips comments and blanks the content of string literals
and quoted identifiers, then requires: not empty, no second statement after a
';', a leading SELECT or WITH, and no DML/DDL keyword anywhere. That last
check is stricter than the spec asked, deliberately: a data-modifying CTE such
as WITH x AS (...) DELETE FROM t begins with WITH and is a single statement,
so the spec's two checks would have accepted it. Second level: the JDBC
connection is opened with setReadOnly(true) - its real effect is read back
with isReadOnly() and stated in the document, since drivers may ignore it -
plus the step's TIMEOUT SEC as query timeout. If any query is rejected,
nothing runs at all. The report, USAGE.md and the designer all say the same
thing: this is a net against mistakes, NOT a guarantee, because a SELECT can
still call a function with side effects; the real guarantee is the rights of
the database account, which is the right place for it.

The report is UTF-8 Markdown at the reportFile param, default
${stepDir}/${feedId}_${stepId}.md. Header: run id, timestamp with the JVM
zone, datasource id/type/host/user/database plus product name, workflow and
step. Per query: its own timestamp, its own duration, the row count, the
statement AS EXECUTED (after variable substitution) in a fenced block, and the
result table with '|' escaped and CR/LF folded to a space so a multi-line
value cannot break the table. The row count is ALWAYS real: the ResultSet is
consumed to the end and only maxRows (default 200) rows are kept for the
table, so Statement.setMaxRows is deliberately not used - it would falsify the
count - and the header says "table truncated to the first N" when they differ.
A password is never written: only datasource id, host and user, and for a
custom datasource the JDBC URL goes through redactJdbcUrl, which masks
password/passwd/pwd values and the user:pw@host form.

Publishes ${reportFile}, ${queriesExecuted} and ${rowsTotal}. failOnEmpty
(default off) fails the step when a query returned no rows, AFTER writing the
report so the evidence survives the failure. The running statement is
registered in control.statement so an operator Stop can cancel it.

Conservative: a new executor id, a new optional child element, a new model
list empty on every existing step, and designer code behind ex ===
'sqlreport'. No existing feed changes behaviour and no new Maven dependency -
plain JDBC through the existing SqlSupport.open. Java 8 throughout.

keyColumn and collect are parsed, stored, round-tripped and shown in the
designer marked "batch 2", but unused; the step log says so when a query
declares them. Collecting query results into run variables is batch 2.

Verified. SqlReportSupport compiled standalone with -source 8 and exercised by
42 assertions, all passing: 16 statements that must be accepted (lowercase,
leading line and block comments, a read-only CTE, a parenthesised UNION, a
trailing ';', a ';' inside a literal, the word DELETE inside a literal, DROP
inside a comment, a column named LAST_UPDATE, GROUPING SETS and OFFSET not
tripping the SET keyword, doubled-quote escapes) and 13 that must be rejected
(null, empty, comment-only, INSERT/UPDATE/DELETE/DROP/CALL/SET, a second
statement with and without a newline, DML hidden behind comments, and the
data-modifying CTE); the Markdown table renderer (pipe escaping, CRLF folding,
short rows padded, no columns, header-only); and redactJdbcUrl (password
param, pwd mid-URL, user:pw@host, nothing-to-redact untouched, and text before
a skipped near-match not being dropped). The <reportQuery> round trip was
proved through a real DOM write-then-parse: a statement containing ';', '&',
'<' and '>' survives intact, attributes round-trip, an absent maxRows falls
back to the step default, and - the point of the tag choice -
textOrAttr("query") returns empty when only reportQuery children exist while a
real <query> child still reads back, so the sql executor is untouched.
designer.html: node --check on all 147k of extracted inline JS passes, zero
literal newline/CR escape sequences, and the only Thymeleaf inlining marker in
the file is the pre-existing commented /*[[${feedId}]]*/. The new
leadingSqlWord helper was extracted and run in node against the same 12 cases
as the Java validator, all matching. String/comment-aware brace and paren
balance is 0/0 on all nine touched Java files, and an import checker confirmed
every type on an added code line is imported, fully qualified, nested in a
resolvable outer type, in java.lang or in the same package.

NOT verified: mvn clean package (Maven Central is unreachable from the chat
sandbox), and everything that needs a live database - the JDBC path, whether a
given driver honours setReadOnly(true), the query timeout, and the report as
actually written by a run. Please build and run one step on deploy.
