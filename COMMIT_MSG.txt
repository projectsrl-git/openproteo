FTPS targets: trust mode by host, and what cannot work here (L2)

Step L2 of the Linux work (finding F7 of the audit).

On a server without the Windows certificate store, a target using
trust mode WINDOWS cannot connect; nothing said so before the first
run, and a new target was proposed that very mode.

- ftps/TrustAdvice and GET /api/ftp-targets/trust: whether the store
  exists on this JVM, and the mode to propose for a NEW target
  (WINDOWS where it exists, JVM elsewhere).
- FTPS targets page: a new target takes the proposed mode; WINDOWS is
  labelled not available and explains itself when chosen; targets that
  would fail are marked in the list; placeholders are neutral.
- SslContexts: the WINDOWS failure says what to choose instead.
- USAGE.md: "The server certificate, on Windows and on Linux".

A saved target is never changed. An absent trust mode still means
WINDOWS on every host - deliberately: FtpsTarget is not touched, and
TrustMode.parse keeps its fallback. Reasons and risk in the spec, 9.4.

If the endpoint does not answer the page behaves as before. No runtime
parameter. README.md and CLAUDE.md not touched.

Verified on Linux (sandbox; Java 1.8.0_432 and JDK 21.0.12): 23
assertions on the real TrustAdvice / TrustMode / FtpsTarget /
SslContexts with keytool-made truststores, 8 mutations; the page in
jsdom, 37, beside the pre-patch page - identical list, hints and save
payload where the store exists - 13 mutations; USAGE.md through
docs.html render(), 21 + the earlier 122; git apply --check on a
second clean clone.
Verified on Windows: nothing.
Not verified on either: the new endpoint (ApiController needs Spring);
a connection to a real FTPS server from Linux.
