JSON table viewer, in the app and as a standalone page

The same treatment the XML viewer got, for JSON, because a list of entities is
what people come to a JSON file to read and reading it as text is the thing it
was never meant to be.

An object becomes a titled block with a Key | Value table. An array of objects
becomes ONE table whose header is the union of the keys found across its
elements, one numbered row per element, with a key that a given element does
not have left visibly blank rather than silently empty, so a ragged list reads
as ragged. An array of scalars becomes a numbered two-column table. A value
that is itself an object or an array shows a short summary - { 4 keys }, [ 12
items ] - and a toggle that opens it in a full-width sub-row, so a deep
document stays navigable instead of becoming a wall of text.

Strings, numbers, booleans and null are coloured apart, and null renders as
null rather than as an empty cell, which is a different thing. Expand all and
Collapse all work on the whole document, and one search box matches keys and
values at once, highlighting matches, dropping branches with none and opening
the path to every hit. A file that is not valid JSON says so, quotes the
parser's own message and stays readable under Code.

Unlike the XML viewer, this one opens ON the table rather than on the source.
That is the point of it; the source stays one click away.

The architecture is the one the XML view established: a light model built
once, tables rendered from it on demand so a large document does not build
every cell before the first paint, and search running on the model rather than
on the DOM so it still finds matches inside branches that have never been
drawn. The .xt-* stylesheet is reused rather than duplicated, which is what
gives light and dark parity for free; only four classes were added, for the
value types.

json_viewer.html in the repository root is the standalone form, built from the
xml_viewer.html shell with the renderer, the loader and the Code-tab printer
swapped. Browse or drag-drop, same table, same search, its own theme switch,
and no upload, no network and no external library - asserted, not assumed.

Verified with jsdom, twice over. Forty assertions on the renderer: the union
of keys in first-seen order, the header and rows of a list of entities, the
hatched cell for a key one element lacks, nested values shown as summaries
rather than flattening the row, an array of scalars, objects as key/value
tables, null rendered as null, collapse closing every nested list while the
root keeps its own key table, search on a value and on a key name with several
matches and case-insensitivity and the path retained, a top-level array which
is the common export shape, and six degenerate documents - empty array, empty
object, null, a number, a string, a boolean - each of which must render
without throwing. Then twenty more driving the standalone page through its
REAL file input, with a real File object, so the load path, the tab switching,
the invalid-JSON banner and the search box are exercised the way a user drives
them rather than by calling internals.

node --check passes on viewer.js and on the standalone page, both with zero
literal newline/CR escape sequences and no external references, and every CSS
variable the new rules use resolves in both themes.

json_viewer.html on a real export - the bigger and more nested the better -
