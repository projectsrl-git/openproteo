Fix: version dialog blocked by IIS, and reportQuery missing from preview

Two field-reported defects from tf0003868, both introduced by earlier batches
in this series.

HTTP 409 is unusable in this deployment. IIS replaces the body of an error
response with its own page (httpErrors existingResponse="Replace"), so the
browser received "The page was not displayed because there was a conflict" as
text/html instead of the JSON payload, and OpenProteo's own proxy-detection
reported it as such. The structural-change version suggestion returned 409, so
it failed every time - and it fires on the FIRST save attempt of any feed that
has runs and gained a step, which is exactly what happened when the RECON
sqlreport step was added to a workflow that had already run. All three save
conflicts now return 200 with ok:false in the body: versionSuggested, and the
two "already exists" branches in /api/workflows/save and
/api/workflows/save-xml. The designer branches on res.j.versionSuggested and
res.j.exists instead of res.st === 409, so a proxy rewriting the status can no
longer swallow the outcome. The rule this leaves for the codebase: never carry
an actionable outcome in a 4xx status, put it in the body.

The GENERATED XML panel is a client-side preview, buildXml() in designer.html,
not the server writer. The sqlreport <reportQuery> element was added to
WorkflowXmlWriter but not to buildXml, so a query typed into the designer
appeared to vanish from the XML. It was not being lost - the save path
serialises it correctly through the writer and reads it back through the
parser - but the preview is what an author checks before saving, and a preview
that disagrees with the file is worse than no preview. buildXml now emits
<reportQuery> with its title, keyColumn, collect and maxRows attributes and
the SQL as element text, skipping a row that is entirely empty.

The lesson is recorded in CLAUDE.md: a new child element needs adding in five
places, not the four of the executor rule - parser, writer, DTO, toDto, and
buildXml in the designer.

Verified. buildXml was extracted from the template and run in node against a
node shaped like the reported one: the element is emitted with all four
attributes, multi-line SQL is preserved in full, a ${var} inside the FROM
survives, maxRows is omitted when unset, an entirely empty query row is
skipped, the step stops being self-closing once it has a child, and xesc
escapes &, < and > as it must for SQL text. node --check on the designer's
inline JS passes with zero literal newline/CR escape sequences and only the
pre-existing commented Thymeleaf marker; brace and paren balance is 0/0 on
ApiController.

NOT verified: mvn clean package, and the two fixes against the real IIS
deployment - which is the only place the 409 behaviour can actually be
confirmed. Please retry the save on tf0003868 first: the version dialog should
now open and offer tf0003868.v1.
