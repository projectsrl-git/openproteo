Specification only. Still no code, no dependency, no registration.

Three answers, folded into the sections they affect rather than appended.

Transarch UNIX is the first target: binary transfers to remote paths. That
moves SITE commands, quoted dataset names and ASCII mode out of batch 2 and
into a new section 15, designed but deferred, because they triple what the
transport must implement and none of them can be exercised against a loopback
server that is not z/OS. Batch 2 is now binary STOR to a path, which is
exactly what can be driven end to end in the sandbox.

The .pfx is named by absolute path in the target, with no configured base
directory. Two consequences are written down instead of being left to surface
later. A target definition becomes specific to the machine it was written on,
so exporting it between environments carries a path that must be rewritten,
and USAGE.md says so beside the field. And because a wrong path is now the
most likely misconfiguration, the step checks the file exists and is readable
before opening any socket, failing with the path it looked for - otherwise a
missing .pfx presents as a failed TLS handshake, which is an error one goes
looking for on the server.

The client in service is never prompted to accept the server certificate. This
produced a fourth trust mode and a new default: trustMode=WINDOWS, reading the
operating system store through KeyStore.getInstance("Windows-ROOT") via
SunMSCAPI, present in Java 8 on Windows. No prompt means Windows already
trusts the issuer; Java does not read that store, it reads cacerts, where an
internal CA distributed by group policy is not present. WINDOWS makes the JVM
trust exactly what the working client trusts. Caveat recorded for the first
handshake: Windows-ROOT holds roots, not intermediates, so if the server does
not send its full chain, Windows-CA must be consulted too.

Section 14 keeps a prediction whose conclusion held and whose reasoning did
not, struck through rather than quietly corrected. It claimed the working
client stores an accepted fingerprint instead of validating a chain. The
opposite is true: it is never prompted at all. trustMode=JVM would still have
failed, but for a different reason, and the answer is WINDOWS rather than
FILE. A prediction that reaches the right conclusion from a wrong premise is
the kind that gets trusted again next time, so the premise is left visible.

Section 13 becomes answered-and-open. Five questions remain and none of them
blocks batch 1 or batch 2. The network path is deferred by agreement to the
point of first use; it remains what section 2 says will fail, and the note on
what a network request needs is kept for when it is raised.
